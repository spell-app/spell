# Lit spike report

`ui-button` (+ `ui-buttons`, `ui-or`), `ui-dropdown` (+ `ui-item`), `ui-icon` / `ui-icons`, `ui-label` /
`ui-labels`, the 13 generic content parts, `ui-divider`, `ui-segment` / `ui-segments` and `ui-container`, on
**Lit 3.3.3** with **standard decorators**, over the shared foundation (`src/`).  Packaged as a SHARED RUNTIME:
`lit` is a peer dependency (external), the element core is split into TWO shared entries (`core.js` for every
family, `forms.js` only for families with a form value), and each family ships only its own classes, sheet,
vocabulary and native fallback.  Measured 2026-09-29 on Apple silicon:  Node 22.17, Vite 8.3.1, Vitest 5.0.2,
Playwright 1.63.0 (headless chromium).  This report holds facts and measurements only;  the comparison and the
recommendation are in `docs/spike-lit-vs-solid.md`.  Every table below is generated by `yarn report`

### Toolchain notes

- **Decorators:**  standard (TC39 2023-11) decorators through the repo's `vite.decorators.ts` (esbuild pre-pass),
  imported, not copied.  Lit properties are `@property() accessor x`.
- **Package:**  `spike/lit/` is a self-contained yarn project:  own `yarn.lock`, `.yarnrc.yml` with
  `yarnPath: ../../.yarn/releases/yarn-4.18.0.cjs`.  `lit` is a `peerDependency` (`^3.3.3`) and a
  `devDependency` (3.3.3, for tests and the vendored copy).
- **Aliases:**  `$` => `../../src`, `$test` => `../../test`, `$shared` => `../shared` (the shared tooling, e.g.
  `PerfRun`).  Spike-internal imports stay relative:  the root `tsconfig.json` has no alias for a spike's own
  `src/` -- a deliberate exception to `AGENTS.md`.
- **Vite config:**  Lightning CSS with the root's `CSS_TARGETS` and `customMedia`;  `resolve.dedupe` for
  `vitest`, `axe-core` and the Lit packages (the root-level `test/*.ts` helpers would otherwise load a second
  vitest);  `server.fs.allow` includes the repo root;  `optimizeDeps.include` lists the `lit` subpaths so the
  first test run doesn't reload mid-run.
- **Lint / format:**  spike-local (`.oxlintrc.json` extends the root's;  the root ignores `spike/**`).
- **Foundation drift fixed in this pass:**  commit `33b89e5` changed three vocabularies after batch 1, and 4 of
  the 156 tests failed at `HEAD` before any shared-runtime work.  Adapted:
  - `ui-icon`:  `style` => `variant` (+ `outline` ~== `variant="regular"`);  an explicit `variant` attribute
    forces the set, otherwise it's inferred from the name (the vocabulary's `solid` default never overrides a
    brand name).  Examples and tests use `variant=`.
  - `ui-label`:  `image` is a string attribute;  present => class `image` (added as `ClassBuilder` extra, since
    the string kind emits no class), non-empty => the `src` of the label's own `img.image`.
  - `ui-divider`:  `divider.css` now keeps a `[hidden]` host at `display: contents` (spacing kept);  the test
    asserts that instead of the old "hides the whole host" bug.

## Bundle

### Method

- **Packaging:**
  - `lit` is external, as a FUNCTION so subpaths match:  `/^lit(\/|$)|^lit-(html|element)(\/|$)|^@lit\//`
    (`LIT_EXTERNAL` in `vite.config.ts`).  `dist/` contains no Lit code (a grep for Lit's
    `litElementVersions` / `reactiveElementVersions` finds nothing) and imports `lit`, `lit/decorators.js`,
    `lit/directives/{if-defined,live,repeat}.js` and `lit/static-html.js` by specifier.
  - **Two shared entries** (`SHARED_ENTRIES` in `vite.config.ts`):
    - `src/core.ts` -- the element core (`src/elements/`:  `UIElement`, `ContentPart`, `VocabularyProperties`,
      owner context, `IconRenderer`) AND the foundation it uses:  `$/util`, `$/vocabulary`, from `$/elements`
      `ClassBuilder` / `Shorthand` / `OwnerContext` / `NativeFallback`, `$/runtime` (the eager loader only),
      `$/icons` (`Icons`), `$/components/components.types`
    - `src/forms.ts` -- `FormElement`, `Validator`, `MenuOptions`;  imported by `dropdown` only.  `ui-button` is
      form-associated through `static formAssociated` + its own internals (submit / reset, no value, validity
      or form API), so it stays on `core`.
  - Every component file imports through ONE path, `../../core` (and `../../forms` where needed), so family
    entries hold none of it:  `button.js` ... `container.js` each `import ... from "./core.js"`, `dropdown.js`
    also from `./forms.js`.  The vocabulary, the sheet and the family's `<name>.fallback.ts` stay direct imports
    (they're the family's own).
  - Two chunking rules the split needed (both in `spike/shared/README.md`):
    - `core.ts` / `forms.ts` import `$/elements` LEAVES, never the barrel:  `export * from "$/elements"` would
      make `Validator` / `MenuOptions` core exports, i.e. core bytes.  So `src/elements/index.ts` leaves
      `FormElement` out (with a `NOTE`).
    - `FormElement` imports the element core through the `core` ENTRY (`../core`), never its leaves, or Rolldown
      hoists what the two share into a third, hashed chunk.
  - `rolldownOptions.preserveEntrySignatures: "allow-extension"`:  with lib mode's default (`strict`) every entry
    became a 0.1 kB facade re-exporting a hashed chunk (`button.js` => `button-<hash>.js`).
  - `button.css` + the button vocabulary land in a shared `button-<hash>.js`:  the dropdown adopts `button.css`
    and reads the button vocabulary.
  - `UIRuntime` and the icon data stay lazy chunks;  `index.js` imports every family.
  - `package.json` `exports`:  `.`, `./index`, `./core`, `./forms`, one per family;  `sideEffects` lists the
    family entries and `index` (they `define()` their tags), not `core` / `forms`.
- **Measuring** (`SpikeMeasure`, identical for every spike):  the spike's own Vite config, built in memory with
  entries `core` + `forms` + one per family;  every emitted module is attributed to a bucket by id
  (`spike.config.ts` `groups`):  `library`, `core`, `shared:forms`, `own:<family>:classes|css|vocabulary|fallback`,
  lazy `runtime` / `icons`.  Each tier is minified (esbuild) and gzipped (level 9) ON ITS OWN, as a page fetches
  them as separate files;  a scenario sums, per family, only the shared entries that family's chunk actually
  imports.
- **Library, two ways:**
  - `library (as used)` -- what the scenarios add:  the named bindings every emitted chunk imports from each
    `lit` specifier (parsed from the chunks' `import { ... } from "lit..."` statements:  `LitElement`, `html`,
    `nothing`, `property`, `state`, `ifDefined`, `live`, `repeat`, static `html` + `literal`), re-exported by one
    entry and bundled once, tree-shaken -- what an app bundler ships, and what `yarn vendor` now vendors
  - `library (full vendored)` -- `peers.ts` bundled as is, every export of all six specifiers:  what the
    import-map pages downloaded before `PeerVendor` was tree-shaken to the used set, kept for comparison
- **Standalone** (for comparison):  each family built ALONE with `lit` bundled and tree-shaken, eager chunks
  summed -- the pre-shared-runtime way of measuring.

### Notes

- **What the shared runtime trades.**  A page with ONE component pays more than a standalone build (33.2 vs
  27.4 kB for a button):  `core` is shared by every family, so it carries what only some need -- `ContentPart` +
  owner context (parts), `IconRenderer`, all of `$/vocabulary`, the `NativeFallback` base.  From the second
  family on, each one costs only its own tier;  a page with every family costs about what standalone builds
  did (94.0 vs 90.8), and "app already ships the library" is the case the packaging is for.
- **`forms` keeps a button page lean:**  `core` went from 18.05 to 14.12 kB when `FormElement` + `Validator` +
  `MenuOptions` moved into `forms` (6.37, loaded by the dropdown only);  a page with only buttons now loads
  `library` + `core` + `button`.
- **Library as used vs full:**  7.51 vs 8.45 kB.  Lit is small and the spike uses most of it (`LitElement`,
  `html`, the directive machinery), so tree-shaking saves under 1 kB;  the standalone builds carried 6.0 (button)
  to 7.5 kB (all) of it.  With `PeerVendor` vendoring only the used bindings, the import-map pages download the
  as-used set too.
- **The own tier grew by the fallbacks:**  each family's `fallback` column is 1.4-2.5 kB here, and about 1.2 kB of
  that is esbuild's lowered-decorator helpers, repeated in every file with a decorator (`@proto static
  vocabulary`).  Net of them (and of `NativeFallback` in `core`, 0.8 kB) the fallbacks are 0.15-1.25 kB each
  (`docs/fallback.md`).  The same helper overhead is in every `classes` column.
- **The old "alone" numbers were measured wrong.**  Batch 1 reported `button` alone 27.7, `dropdown` 45.0,
  `icon` 22.1, `label` 24.6, `parts` 26.5, `divider` 19.8, `segment` 21.6, `container` 17.5, all eight 84.6 kB.
  The old `measure.ts` passed each single entry INLINE next to `configFile`, and Vite's `mergeConfig()` UNIONS
  `build.lib.entry` objects:  every "alone" build really had all eight entries, so its closure was split into
  shared chunks gzipped separately (verified:  an inline `{ button }` entry emits all ten entry chunks).
  `SpikeMeasure` loads the config file once and replaces the entries;  its standalone column is the corrected
  "alone".  `PAPERCUTS.md` has the entry.
- **Core breakdown** (batch-1 measurements, each group gzipped alone, before the `forms` split):  spike element
  core 5.9, `$/vocabulary` 4.3, `$/elements` 7.2 (`ClassBuilder`, `Shorthand`, `MenuOptions`, `Validator`,
  `OwnerContext`), `$/icons` + runtime loader + `$/util` 2.9.  `ContentPart` + `PartOwners` + `OwnerController`
  are about 1.1 of the element core;  `lit/static-html.js` (a part's varying tag) about 0.5 of the library.
- **Decorator helpers:**  esbuild's lowered decorator helpers cost about 2.2 kB min (1.2 kB gzip) per chunk that
  has decorators (batch 0).
- **Tree shaking:**  decorated classes count as side effects, so a barrel that re-exports a decorated class
  (`FormElement`) pulls it into every importer -- one reason `FormElement` sits in `forms`, not the `core`
  barrel.
- **Icon data is lazy:**  `Icons.ts` loads the alias maps on first use (0.25 kB left eager), and its per-chunk
  `CHUNK_LOADERS` table keeps `search.json` out of the build.
- **`label` doesn't import `parts.css`:**  a statistic's label adopts it by registry name (`PARTS_SHEET`);
  whoever loads the owner loads the parts.
- **No virtualizer:**  items render only while the menu is open.
- **Runtime:**  the lazy `UIRuntime` chunk alone is about 27 kB min+gz, against the plan's budget of 20 kB for
  runtime plus tokens.

## Ergonomics

### Declaring attributes and properties

- It takes one line:  `class UIButton extends UIElement.for(buttonVocabulary)`.
  - `for()` calls Lit's `createProperty()` for each vocabulary attribute:  the attribute name comes from the
    vocabulary, the converter from `Converters` by kind, primitives reflect, `json` attributes are properties
    only.
  - A mapped type derives every property type from the `as const` vocabulary, so there are no hand-written
    fields;  a component can retype what the vocabulary can't express through a type argument
    (`value: DropdownValue`).
  - Event, slot, part and text names are type-checked too (`EventName<this["vocabulary"]>` ...):
    `this.emit("ui-bogus")` is a compile error.  Templates read slot and part names through `slotName()` /
    `partName()`, never literals.
- **Booleans** use `Converters.boolean` (`yes` / `no` work) and reflect as `""` or a removed attribute.
  **Arrays** are plain properties, reflected as `a,b`.  **`options`** is a property only.
- **Defaults:**  Lit's `useDefault` keeps defaults out of the DOM and restores them when an attribute is removed.
  It only works when the start value isn't `undefined`;  otherwise Lit swallows the first real change.
- **Reserved names:**  a vocabulary attribute whose property would shadow an `HTMLElement` member (`style`,
  `hidden`, `title` ...) is renamed `<noun><Name>` by `VocabularyProperties.propertyName()` (`dividerHidden`);
  the attribute keeps its name.  A Lit property named `style` replaces the host's `CSSStyleDeclaration`.
- **Standard decorators** worked everywhere:  `@proto static`, `@state() accessor`,
  `@property({ attribute: false }) accessor content`.  `@customElement` isn't used:  tags come from the
  vocabulary (`UIButton.define()`).  `@proto`'s `protoDefined` hook mirrors `delegatesFocus` into Lit's
  `shadowRootOptions`, which SSR reads.

### Templating

- Lit templates map 1:1 onto the markup contract, using keyed `repeat()`, `live()` and `ifDefined()`.
- A part's varying tag (`div` / `span` / `time` / `a` / `h1`-`h6`) needs `lit/static-html.js` `literal`s;  one
  template covers every part root.
- `Icons.svg()` returns a DOM node that Lit would replace on every render;  `IconRenderer` produces the same
  `<svg>` markup as a template instead.

### Owner context and content parts

- **`PartOwners`** is a static, page-wide registry filled by `UIElement.define()`:  part noun => (owner tag =>
  owner noun), from each vocabulary's `ownsParts`, canonical and translated tags alike;  tag => "is a content
  part";  the connected `OwnerController`s.
- **`find()`** wraps `OwnerContext.find()`.  Its `barrier` is any registered component that is not a part;
  owners match before the barrier.  A header inside a segment inside a card stays standalone, while an app's own
  unregistered wrappers don't block.  Lookup is by tag, so upgrade order never matters.
- **`OwnerController`** is a Lit `ReactiveController` used by `ContentPart`, `UIIcon` (`direct: true`, parent
  must be `<ui-icons>`) and `UILabel` (a statistic's `label`):  it resolves on `hostConnected` (which also covers
  reparenting), swaps `:state(in-<owner>)` (never the `in-<owner>` class), and calls `requestUpdate()` plus an
  optional `onChange` (the label re-adopts sheets with `parts`).
- **Re-resolution:**  every `UIElement` shadow root reports `slotchange` (with `flatten`) to
  `PartOwners.reslotted()`, which re-resolves tracked elements in or under the newly assigned nodes.  A late
  owner registration re-resolves every connected tracker.
- **Owner tokens:**  a header in a plain segment inside an inverted one reads `--ui-inverted: 0`;  reversed, it
  reads 1 with `color-scheme: dark`.  `--ui-part` is declared on every part root by `parts.css`.
- **`OwnerStub`** (`x-card`, `x-feed`, `x-statistic` ...) stands in for owners that don't exist yet:  light-DOM
  elements registered as real owners, so the demo and axe exercise the production lookup path.
- **Platform limits hit:**
  - nobody tells an element it was re-slotted:  only the slot gets `slotchange`, so owners report it.  A part
    slotted into a non-`UIElement` owner that re-slots it isn't re-resolved until it reconnects.
  - `slotchange` fires after the owner's first render assigns its slots, so a part resolves twice (connect, then
    `slotchange`);  tests wait two `updateComplete` rounds.
  - `:state()` on a `display: contents` host matches fine in `:host(:state(x)) > .root`.
  - Chrome keeps a `display: contents` host with an internals `role=img` + `ariaLabel` in the accessibility tree
    (`image "Home"`) and drops it when `ariaHidden` -- verified against Chrome's real tree through CDP
    (`testing/AXTree.ts`, `Accessibility.getPartialAXTree`), not only axe.

### Per component

- **Button, dropdown:**  the bulk of batch 0.  `<a>` vs `<button>` needs two templates.
- **Icon:**  trivial;  host ARIA through internals (`role=img`, `ariaLabel`, `ariaHidden`) is three assignments.
  `variant` / `outline` pick the set (see "Toolchain notes").
- **Label:**  the most logic in batch 1:  `<a>` vs `<span>` roots, icon-only detection, the `image` string
  attribute (class vs URL), the statistic-label mode.  The contract's `<slot name="icon">svg</slot>` fallback
  works here (a descendant `.icon svg` selector).  An icon-only `<span>` root with a forwarded `aria-label`
  becomes `role=img`, since `aria-label` is prohibited on a generic element.
- **Parts:**  the easiest, once `ContentPart` existed.  The owned-header decision is a single `if (this.owner)`,
  because `OwnerController` re-renders the host when the owner changes.
- **Divider, segment, container:**  mechanical, 18-32 code lines each.  The segment declares `--ui-inverted`
  inline on its root;  `disabled` makes the root `inert` (reaches slotted content through the flat tree);
  `loading` sets host `aria-busy` and renders a visually hidden `role=status`.  A scrolling segment, container or
  modal `ui-content` gets `tabindex=0` (axe `scrollable-region-focusable`).

### What fought the library

- A member-name clash (a `part()` method vs `HTMLElement.part`) shows up as "Unable to resolve signature of
  property decorator" on EVERY decorator in every subclass, far from the real cause.
- Decorated classes count as side effects, which defeats tree shaking through barrels.
- `useDefault` with an `undefined` start value swallows the first change (above).
- The caret `<span>` must stay whitespace-free for `:empty`;  oxfmt reflows templates, so a test guards it.

### What fought the conventions

- Classes-over-functions fits Lit naturally, and vocabulary-driven names fit via `createProperty()`.
- A `display: contents` host swallows inline box styles:  `style="width: 2em"` on `<ui-avatar>` did nothing;  the
  example sizes through `::part(avatar)` instead.  Adding an owner-only style needs a `<style>` in the page --
  correct, but surprising to authors.
- Spike-internal imports are relative (no alias for a spike's own `src/`).
- **Chunking vs `AGENTS.md`:**  `core.ts` / `forms.ts` import `$/elements` leaves (not the barrel), and
  `FormElement` imports `../core` instead of its peer `./UIElement` -- both to steer Rolldown's chunk assignment
  (Bundle).

## Error handling & native fallback

- **Before:**  a throw in `render()` escaped Lit's `performUpdate()`, rejected `updateComplete` and surfaced as an
  unhandled rejection on the NEXT update;  the element kept its last good DOM, frozen.  Lit elements update
  independently, so siblings never stopped -- there was no halt to isolate, only nothing to degrade to.
- **Hook** (`UIElement`, about 35 code lines):
  - `scheduleUpdate()` runs every update through `guardedUpdate()`, a `try` around Lit's `performUpdate()`:  it
    catches `willUpdate()`, `update()` / `render()` (Lit rethrows after marking the update done) and
    `firstUpdated()` / `updated()` (they throw straight through).
  - `failed()`, on the first failure only:  ONE `console.error` naming the tag with the cause
    (`<ui-button> failed:`), `:state(errored)`, a cancelable, bubbling, composed `ui-error` (`detail: { error }`,
    `ERROR_EVENT` in `elements.types.ts`;  no vocabulary names it yet), then -- unless cancelled -- the family's
    `@proto static Fallback`:  `ButtonFallback.render(host, shadowRoot, error, internals)` ... builds its native
    DOM into the shadow root, synchronously.  Cancelled, the shadow root is emptied instead (the last good render
    would never update again) and the page takes over.
  - `shouldUpdate()` returns false from then on:  Lit would otherwise re-render over the fallback, and
    `FormElement.updated()` would overwrite the fallback's form value.
  - An element without a fallback (groups, `ui-item`, `ui-or`) gets a bare `<slot>`, so its children stay
    visible.  Per-family fallbacks live in the family's chunk:  `UIButton.Fallback = ButtonFallback`, ...;  the
    13 parts share `ContentPartFallback` through `PartElement`.  The markup is library-neutral
    (`src/components/<name>/<name>.fallback.ts`), so both spikes render the identical thing and the component's
    adopted sheet styles it.
  - NOTE: `Fallback`, capitalized (a class), like the Solid spike's:  it can't clash with a vocabulary
    attribute's property.
- **Bytes per family** (`docs/fallback.md`, net of shared code and decorator helpers, gzip):  base
  `NativeFallback` 0.80 (in `core`), button 0.68, dropdown 1.25, icon 0.32, label 0.30, parts (all 13) 0.40,
  divider 0.23, segment 0.20, container 0.15 -- about 3.5 kB for all eight.  In this build, each family's
  `fallback` column (Bundle) is 1.4-2.5 kB because every file carries its own lowered-decorator helpers.
- **What degrades** (`docs/fallback.md`):
  - button:  `ui-toggle`, the icon glyph and icon / label slots, the joined label, `animated`, the spinner;  a
    host click handler can't veto submit
  - dropdown:  a native `<select>` (multiple, optgroups) instead of the combobox:  no search, additions,
    clearable, max-selections, value labels, option icons / images / descriptions, `ui-open` / `-close` /
    `-search` / `-add` / `-remove`;  the native select's keyboard pattern;  `readonly` becomes disabled.  Form
    value, validity, `host.value` and `ui-change` keep working.
  - icon:  the glyph;  label:  delete button, icon, image;  divider:  icon shorthand;  parts:
    `:state(in-<owner>)` styling;  everywhere:  idref ARIA can't cross the shadow boundary.
- **Tests:**  `spike/shared/tests/fallback.cases.ts`, library-agnostic, run by `src/fallback.test.ts` through a
  `FallbackAdapter` (`breakRender()` patches the element's `render()` to throw and calls `requestUpdate()`;
  `settle()` awaits every element's `updateComplete`, twice).  All 7 pass:
  - a throw in render shows the native fallback, with exactly one tagged `console.error`, one `ui-error`
    (bubbles, composed, cancelable, `detail.error`), `:state(errored)`
  - a cancelled `ui-error` keeps the fallback out
  - every family renders its fallback root (and is really `:state(errored)`)
  - a sibling of a failed element still updates;  a new element still renders
  - the fallback button submits its form with `name=value` (`a=1&action=save`), only during the submit
  - the fallback select starts on the chosen value, keeps the form value, and a change updates the form value,
    `host.value` and fires one `ui-change`
  - axe passes on every family's fallback (`color-contrast` off)
- **Demo:**  `demo/fallback.html` (via `yarn serve`, and a smoke check page) shows each family working beside its
  failed copy;  the failed submit button submits `[["action","save"]]`.
