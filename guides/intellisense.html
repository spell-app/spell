VS Code

Type <ui-button sise="large"> in a .tsx file, and it's red: in the editor, and in yarn ts. Fix it to size=", and the eight sizes complete, mini to massive, each with its docs on hover.

That's one half of what Spell's VS Code extension does: custom elements, in JSX, HTML and CSS. The other half is Spell itself: open a .spell file, and you get errors as you type, the TypeScript, JavaScript or Python it compiles to beside it, and the project running in a panel. Both come from your checkout of the kit, as it is on disk.

  • One extension, Spell, built from the app folder's vscode/: spell app vscode builds and installs it. It isn't on the Marketplace.
  • In a .spell file: the language server, the compiled TS, JS and PY views, Run Project and Run Tests, the bubbly look, and Spell's themes as VS Code colour themes.
  • The .vsix carries no Spell: it runs the language server of the checkout your window is on, so a change to the parser shows once the server restarts.
  • In JSX, every one of Spell UI's 149 <ui-*> tags completes, shows its docs on hover, and is checked: a misspelt attribute or a wrong value is red, in the editor and in yarn ts.
  • Each tag's events are typed, so event.detail is known.
  • In HTML and CSS files, Spell UI's tags, custom properties, parts and states complete, in every window, each tag once.
  • The elements help adds what types can't say: slot names, part names, and misspelt dashed attributes. It runs in the editor only.
  • The editor's TypeScript stays TypeScript 7: nothing to switch, no prompt.
  • The slot, part and HTML and CSS help are built into the extension: after spell app vscode, reload the window (The elements help).
  • A vocabulary change shows in HTML and CSS files after that rebuild too.

Most language extensions carry their language server inside them. Spell's carries no Spell at all: when a window opens its first .spell file, the extension starts THAT window's checkout's language server, from source, with the kit's tsx.

  • So the editor runs Spell as it is on disk: change a rule in the parser, restart the server, and the squiggles follow. No rebuild, no reinstall.
  • Which checkout: the spell.parserRoot setting when it's set, else the window's folders. The Output panel's Spell channel says which it picked, and why.
  • A window with no .spell file open starts no server.

Typing <ui-button in a .tsx file:

  • every attribute the button has completes, then its values: size=" offers the eight sizes, mini to massive
  • hovering an attribute shows its description, its values and its default
  • a misspelt name (sise="large") or a value it doesn't take is an error
  • still allowed: HTML's global attributes (class, id, slot, style, onClick ...), aria-*, and any name with a dash in it (Limits)

How values are typed:

  • a flag: basic, basic={true} or basic=""
    • basic={false} removes it
  • a number: {5} or "5"
  • a shared value set (the hues, the sizes): its real list, not plain text
  • rich data (an object, an array, a function) as a plain prop, options={[...]}: it reaches the element whole, as its property
  • prop:options, and prop: for every attribute, are marked deprecated: only compiled Spell writes them
generated, shortened · Spell UI's JSX types · 12 lines 
export interface UIButtonAttributes {
  /**
   * Size, `mini` ... `massive`;  `medium` is the default.
   * - takes:  `mini` · `tiny` · `small` · `medium` · `large` · `big` · `huge` · `massive`
   */
  size?: "mini" | "tiny" | "small" | "medium" | "large" | "big" | "huge" | "massive"
  /** `size`, as the DOM element's property. */
  "prop:size"?: "mini" | "tiny" | "small" | "medium" | "large" | "big" | "huge" | "massive"
}

  • In an .html file, <ui- completes Spell UI's tags, then their attributes and values, with docs.
  • In a .css file:
    • custom properties complete where you set them, with their default and their tag in the hover: Spell UI's 1,604
    • ::part() names: 245
    • :state() names: 189
  • Parts and states are offered after any selector, because VS Code's CSS data can't tie a name to a tag. Each one's docs list the tags that have it instead.
  • The catch: inside var(--, VS Code completes only the variables the file itself declares. The data helps where you set a property, not where you read it.
  • Both data files are written by Spell UI's yarn site:data, and copied into the extension when it's built, so they work in every window, an epic's too.
    • The catch: a vocabulary change shows here after the next spell app vscode and a window reload.

A TypeScript program gets the exact <ui-*> types by importing them once, in any of its files. Its .types.ts file is a good home.

any one file of the program · 1 line 
import type {} from "spell/ui/jsx"
  • Then every <ui-*> tag in that program's JSX is checked.
  • Not through the tsconfig's types list: that finds packages, not a package's files.
  • Type-only: nothing is added at run time.
  • Each tag's types can be imported by name too, for a wrapper's props: UIButtonAttributes (its own attributes), UIMenuJSXAttributes (those plus HTML's).

Who does it today:

  • Spell UI itself, its docs elements and its tests
  • the app, in solid.types.ts
  • the epic pages' elements, in EpicPage.types.ts
  • the Spell compiler's type check of compiled Spell (typecheck.ts)

Where the types come from:

  • ElementManifests writes them, one file, as part of Spell UI's yarn site:data, beside the HTML and CSS data and the Custom Elements Manifest.
  • A test fails while the file is stale: run yarn site:data after changing a vocabulary.
  • The file is large, about 62,000 lines, and committed: jsx.ts.
  • Never edit it by hand.

Every event a tag sends is typed, with its event.detail, in two places.

events, in JSX and plain code · 6 lines 
// JSX:  on- plus the event's name, one prop per event the tag sends
<ui-input on-ui-changed={(event) => setName(event.detail.value)} />

// plain code:  the tag's own element knows its events
const input = document.querySelector("ui-input")
input?.addEventListener("ui-changed", (event) => event.detail.value)
  • In JSX: on-ui-changed, typed per tag. Solid hands the function to the element, which listens for the event.
    • The list of props is closed, but a misspelt one has a dash, so only the elements help catches it.
  • In plain code: querySelector("ui-input"), or a JSX ref, gives an element whose addEventListener() completes its events, each detail exact.
    • Its other members (value, open() ...) aren't typed there: cast to the DOM element class for those.
  • On the document, or any other element: every ui-* event name completes, but its detail is unknown.
    • Narrow it, or listen on the tag.
  • A detail's type names Spell UI's real types (close reasons, form changes ...): a name the generator doesn't know makes yarn site:data fail, naming the table to add it to.

The extension adds what types can't say, in every .tsx and .jsx file. It reads the Custom Elements Manifest of the file's package and its dependencies, so any set that ships one gets it.

  • slot=" on a child of a custom tag lists the parent's slots, with their descriptions.
  • part=" in a component's own JSX lists its parts.
  • A misspelt slot, part or dashed attribute gets a yellow warning in the Problems list, with "did you mean" when one is close.
    • Always allowed besides the tag's own: data-*, aria-*, and an on- prop for each event the tag sends.
  • Each file reads its own checkout's manifests: in an epic's window, a worktree's file gets the worktree's.
  • A manifest is re-read when it changes: a new yarn site:data shows at the next keystroke.
  • The checks are the kit's JsxElementHelp, which gives its results as plain data; the extension's ElementsHelp shows them as completions and warnings.
  • The editor's own TypeScript stays TypeScript 7. Your settings are left alone, and nothing asks to switch.
  • Inside, the extension reads the JSX with TypeScript 6's JavaScript API, which it carries: TypeScript 7 has none yet, and loads no plugins.
  • It turns on as a window opens its first .tsx or .jsx file.
  • A change to the checks shows after spell app vscode, then "Reload Window".
  • Not working? The Output panel's "Spell Elements" channel lists the manifests each package found, and anything that failed.
  • A misspelt dashed name passes tsc: TypeScript never checks a JSX attribute with a dash in it, which is how data-* stays allowed.
    • <ui-button text-alin="x"> passes, where sise="large" is an error.
    • A dashed name the vocabulary does name is still typed: a wrong value is caught.
    • The elements help warns on the name in the editor; yarn ts doesn't run it.
  • Plain text needs a cast: a value your own types hold as a string (a card's colour) is handed to a tag's attribute with a cast to its type, UICardJSXAttributes["background"].
  • HTML and CSS data are the extension's build: they show what Spell UI had when the extension was last built, from the checkout it was built in.
    • After a vocabulary change: yarn site:data, then spell app vscode.
    • The JSX help reads the manifests live, so it's never behind.
  • Which children a tag takes isn't checked: no vocabulary says so yet.
  • The epic pages' and the app's own tags have loose JSX types (any attribute) and no Custom Elements Manifest, so their slots and parts aren't completed either.
  • "Show Tree for This Line", in a .spell file's right-click menu, has no command behind it yet: spell parse --tree "<the line>" prints that tree in a terminal.
