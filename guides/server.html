The Page Server

  "pid": 75355,
  "port": 4747,
  "root": "~/www/spell",
  "started": "2026-11-22T02:46:14.087Z",
  "branch": "main",

  "base": "http://127.0.0.1:4747"
}

That's the server every Spell page is read on: the guides, the epic pages, the component sets' docs, the editor's API, and every epic's worktree, on one port. There is ONE per kit, whichever folder of it you ask from.

If you've used npx serve, it starts out the same: files go out exactly as they are on disk, with no build step. Then it adds what that doesn't: live reload, a router with Express's names, and a way for a page to save a section of itself back to disk.

Written for: anyone opening, writing or serving a page, or adding routes to the page server Checked: 2026-11-21, every command and address against that day's code and a running server The reference beside it, with every address, call, setting and file: the server README
  • It's the kit's server folder, imported as spell/server, namespace SRV: a library, and the page server built on it.
  • It starts from the kit's root only, on 4747 when that's free, else any free port (SPELL_SERVER_PORT overrides).
  • A page gets five lines added to its head: Spell's favicon, the page's facts as window.SPELL_SERVER, and the live reload client. The rest is the file, byte for byte.
  • The main checkout's server serves every epic's worktree too, at /worktrees/<epic>/....
  • The server names no folder of its own: each folder of the kit brings its part of the settings, and its route modules.
  • It keeps out other web pages, not other programs on your machine: loopback only, a host check, a token per run, same-origin writes.
command what it does
spell server start start it in the background if it isn't running, and print where it is (JSON): "launched": true when this call started it
spell server start all every web server of the checkout: the page server, the editor, Spell UI's bundle
spell server status the running server's facts (JSON), or not running and exit 1
spell server stop [all] stop it; all: the app's editor with it, even one left running
spell server url <file> start it if need be, then print the address that serves the file
spell server local run it in the foreground, until Ctrl-C
spell server prune stop the page and Vite servers whose checkout is gone
spell bundle [--stale] build the bundles it serves (Spell UI's site ...); check says which are stale
spell app serve [project] the page server and the editor together, then opens the editor
epic pages open [page] show a page in Chrome, or in VS Code's side bar with --vs
  • Flags, after any verb: --root <dir> (another kit's root), --port <n>, --spaces <dir> (the projects folder; it also gets an editor of its own).
  • A tool that shows a page never assumes a server is up: it asks for one, and starts it if need be. A server older than its own code is restarted, so after a merge the next opener gets the new routes.
  • Its facts go in .spell-server.json at the kit's root, where the openers find them; its output, in colour, in .spell-server.log.
  • Cold, it answers in about a second and a half: it loads its route modules before it listens.
  • The catch: pointed at any folder but a kit's root, it refuses to start, and says where the root is.

A request meets the route modules first, in the order the settings list them. Whatever they don't answer is a file: from the kit, then the epic folder, then a folder the settings name.

address what it serves
/ a redirect to the docs home, /pages/index.html
/guides/, /epics/, /sagas/, /pages/ the kit's own guides/ first (the guides that ship with Spell), then the epic folder
/worktrees/<w>/... an epic's worktree, the same addresses inside; on the main checkout's server only
/components/<set>/ a component set's docs: /components/ui/ is Spell UI's
/_epic/assets/, /_epic/pack/, /templates/ the epic engine's page scripts and styles, its elements, its templates
/editor a redirect to the running editor; while it isn't up, a 503 page saying so
/api/server the server's facts: what spell server status prints
/api/... saving pages and files, then each route module's calls; the editor's API last
anything else the kit's own files, and every folder's inside it: /app/app/docs/index.html
  • Old addresses get no redirect: they answer "not found".
  • Every call under /api/, and which module answers it: the server README, "One port, every address".

Vite swaps a changed module into the running page. This server tells the page which FILE changed, and the page decides: patch itself, swap a stylesheet, or reload.

a page's socket, while a file it shows is written twice, 100 ms apart · 2 lines 
{"event":"hello","data":{"run":"852fc1fa"}}                as the socket opens
{"event":"change","data":{"path":"/guides/hello.html"}}    262 ms after the second write
  • Each path waits for 250 ms of quiet: a save is often a write, then a formatter.
  • The page's own file is patched in place or reloaded; a stylesheet is swapped with no reload; a script reloads the page, keeping the scroll.
  • One websocket a page, never an EventSource: each held-open request takes one of Chrome's six connections per host, for good, and every VS Code window shares them.
  • Never while you type: an "Updated: reload" pill waits until the field loses focus.
  • A server restart sends a new run id, and a page from the old run reloads.
  • Only watched folders report: a file anywhere else can change all day, and no page hears of it.

The site header's pencil turns edit mode on: hover outlines any element with an id, and "edit" opens its HTML. The save splices that element's bytes into the file.

what the section editor sends, by hand · 9 lines 
GET   /api/pages?path=/guides/hello.html&id=hello
200   {"path":"/guides/hello.html","etag":"\"4c-1a1614c434d\"","html":"<h1 id=\"hello\">Hello, again!</h1>"}

PATCH /api/pages?path=/guides/hello.html      x-server-token, If-Match: "4c-1a1614c434d"
      {"id":"hello","html":"<h1 id=\"hello\">Hello, edited</h1>"}
200   {"path":"/guides/hello.html","etag":"\"4c-1a1614c4837\""}

PATCH the same again, with the same If-Match
409   {"error":"the file changed since it was loaded:  reload it","etag":"\"4c-1a1614c4837\""}
  • Only the element's own bytes change, so git diff shows only the edit.
  • Nothing is committed: the change waits in the working tree.
  • Two people editing one section: the second save gets the 409, and the editor says to reload. No If-Match at all is a 428.
  • A script can do the same: SPELL_SERVER.editPage({ id, html }), on any page the server sent.
  • The edge: only inside the folders the settings call writable (the epic folder's epics, guides, pages); anywhere else is a 403 that says where you can write.

An epic is worked in its own worktree, but its pages are read on the main checkout's server. Vite runs a dev server per project; here one port, one tab and one live reload serve however many epics are open.

  • spell server url in a worktree hands out the main server's address for it: http://127.0.0.1:4747/worktrees/<epic>/....
  • A page served from a worktree is told its branch and worktree name, for the header's badge.
  • The epic folder is served after each worktree's own files, so /worktrees/<w>/epics/... works, from one shared copy.
  • The server knows nothing of epics: a route module of the epic engine's tells it where the worktrees and the epic folder are.

An Express server is an app you write. This one is an app you configure: settings name the folders, and route modules bring the code.

  • Each folder of the kit declares its own part, in its package.json's "pageServer"; the epic folder's is its page-server.json5.
  • They're merged as the server starts: the kit's own, the epic folder's, then each folder's, lowest first.
Spell UI's whole part, from its package.json · 4 lines 
"pageServer": {
  "bundles": ["site/_assets"],
  "componentSets": { "ui": { "name": "Spell UI", "dir": "docs", "assets": "site/_assets" } }
}

A route module is a file whose default export is a name and a setup(), which runs once, before the server listens. The server imports none: it loads each by its path from the settings.

a route module: listed in a folder's routes, GET /api/hello?name=Spell answered {"hello":"Spell"} · 10 lines 
import type { RouteModule } from "spell/server/page"

const helloRoutes: RouteModule = {
  name: "hello",
  setup({ router }) {
    router.get("/api/hello", (request, reply) => reply.json({ hello: request.query.name ?? "world" }))
  }
}

export default helloRoutes
  • Its routes run before the static files.
  • What setup() gets: the router; the guard, for routes that change something; live reload's watcher; the server itself; and onListening() and onStop(), for a child process such as the editor.
  • Order matters: the editor's /api router ends in a catch-all 404, so it's listed last.
  • A module that fails to load is logged, not fatal.

A web page in some other tab can send requests to 127.0.0.1 too. So the server checks:

real answers from a running page server, one per request · 7 lines 
{"error":"unknown host"}                                403
{"error":"hidden file:  /.spell-server.json"}           403
{"error":"outside the root:  /../etc/passwd"}           403
{"error":"bad path:  /guides%2Fserver.html"}            400
{"error":"bad token:  reload the page"}                 403
{"error":"bad path:  /guides/server.html%00"}           400
{"error":"wrong origin"}                                403
  • Loopback only (127.0.0.1), and a host check on every request, against DNS rebinding.
  • A write token per run, which only the pages it served know (window.SPELL_SERVER.token), sent as x-server-token.
  • Writes only from the same origin, and only inside the writable folders.
  • One path check for every file: .., NUL bytes and encoded slashes are refused; dot files are never served.
  • The editor's API takes no token: its one check is the origin.
  • The edge: these keep out other web pages, not other programs on your machine. Any local program can fetch a page and read its token.

A Spell page is hand-written HTML in <ui-*> elements, with no build step to read it. Each kind of page has ONE name, and most start from a template, the epic engine's epic/templates/.

kind what it's for template
guide explains a topic, like this page durable.html
cheatsheet an API at a glance, as cards you filter cheatsheet.html
epic page an epic's plan: its phases, items and log the epic tool's own
saga page an epic of epics: what its epics did, its ideas, its epics' cards the epic tool's own
details page one question explained with a picture, answered on the page details.html
Feature Set a details page that's a ranked list to pick from, whose sections and items you can name (S1F1) and reorder epic ask create <slug> --template feature-set --from <data.json5>
review page several calls to go through at once: keep, change, talk over review.html
choice page a table of names Claude recommends, typed over, then "Do it" syntax-choices.html
run page a command asks, the person answers each row and sends, and the command carries on served by the epic engine, never copied
commands page which command, skill or script does what commands.html
components page one element: its examples, attributes and look spell-ui-docs.html
components guide a component set's pages that aren't one element: home, getting started, theming component-set-docs.html
reference page made from its source each time: a place's, the commands pages, the core reference none: drawn from its source
home page, list page the docs' front page, and each top-bar tab's page: a card per page none: epic pages index writes them
changelog what the repo shipped, newest first none: its header comment has an entry's markup
template the starting point for one kind of page --
  • Where they live: the guides that ship with Spell in the kit's guides/ folder, versioned with the code; epic pages, sagas, details pages and the rest in the epic folder, beside the kit.
  • A page loads ONE classic script, /_epic/assets/spell-ui.js (Solid, Spell UI and the page runtime, bundled), and one stylesheet, /_epic/assets/spell-doc.css.
  • The toolbar in its sticky header is built from its top-level sections when it loads, so it never drifts from them. Folds are remembered per page.
  • Start one with epic pages create durable <page> --title "..."; link its code spans with the epic engine's doc-links.js, then check it with doc-links.js --check.
  • Every tool that writes a page calls the same steps: links (SRV.Linker), then formatting (SRV.formatHTML()), then the write. So pages come out alike, whoever wrote them.
  • No TypeScript, no module swapped in place: a .ts file goes out as text/plain, to read. The editor, which needs both, runs on Vite.
  • Bundles show as last built: a Spell UI change shows on /components/ui/ after spell bundle --stale, or the server's next start.
  • A worktree deleted by hand leaves its server running: spell server prune stops it.
  • The docs home needs the epic folder, which someone new hasn't got: start at /components/ui/, which needs only the kit.
  • It isn't the Python server: spell run <project> --target py starts a different, much smaller one, which runs one program.
