Start Claude Code in the kit, and before you type a word, the agent has read the kit's AGENTS.md and the hub of WWOD, "What Would Owen Do?", the house style every folder shares. Those rules name their reader: WWOD opens "Audience: AI coding agents -- follow these over your defaults".

A rule can be pointed at exactly: WWOD §5 › "Sentinel errors as control flow" names one bullet, and spell wwod check proves every citation like it still lands.

Written for: anyone about to read, cite, add or change a rule, or set up a project's agents with them Checked: 2026-11-21, every file and command against that day's code The reference beside it: the agents README, and WWOD's own README.md
  • WWOD is a set of Markdown files an agent reads, not a linter. It lives in the kit's agents/wwod/, tracked with the code: edit it there.
  • A HUB every task needs (WWOD.md, §1-7), SPOKES read when the work touches their topic (§8-20), and one rule a project opts in to, §21.
  • Spell opts in to §21: the code is the spec, so a test that disagrees with the code is rewritten to match it.
  • One home per rule: house style in WWOD, what's about one folder in its AGENTS.md, how Solid 2 works in the Solid 2 rules.
  • spell wwod init hands WWOD and the Solid 2 rules to another project's agents: they ship in the npm spell package.
  • Problems known and lived with go in three logs: code debt, suspected bugs, papercuts.

Every rule has exactly one home, picked by what it's about.

  • WWOD: house style, how we write any code in any folder. Naming, errors, classes, tests ...
  • An AGENTS.md: the kit's holds what's about the kit and across its folders; a big folder's, what's about it; a sub-folder's, what's local to it.
  • The Solid 2 rules: how Solid 2 itself works, measured. The house style on top of it is WWOD §17.
  • Anywhere else a rule is needed, it's one line pointing home: SEE: WWOD §N › "title".

An agent reads from the general to the specific: the kit, the folder it works in, the task's rules.

  1. The kit's CLAUDE.md, as every Claude Code session starts: it @-imports the next two and §21, then adds the Claude-only rules.
  2. The kit's AGENTS.md: the kit and what's across its folders. Codex reads it itself.
  3. WWOD's hub, through CLAUDE.md.
  4. A big folder's AGENTS.md, then its sub-folder's, when the session first works there.
  5. WWOD's spoke for the task, as the hub's table says, before writing.
  6. The Solid 2 rules, IN FULL, before any Solid code: they're kept out of the imports, being long.
  • Only the first three load by themselves; the agent opens the rest when they tell it to.
  • Every big folder has an agents link at its root to the kit's, made by every install, so its rules can name agents/wwod/WWOD.md. The epic folder has none: in a plugin, a root agents/ loads as the plugin's agent types.
  • A rule is a bullet with a bold title (or a ### heading) under a numbered section.
  • Cite it as WWOD §N › "title"; a whole section as WWOD §18. Inside WWOD, a bare §5 means WWOD's.
  • Renumbering is allowed: the check finds every citation it breaks.
one whole rule, from §6 · 11 lines 
- **User-facing strings stay inline**, where they're used -- EXCEPT in code that speaks more than one language:
  - Spell UI:  its vocabularies (`UIButton.en.ts`) and dictionaries (`UIButton.es.ts`)
  - the editor app (`spell/app/app`):  every text it shows people is a key in `AppTexts.en.ts`,
    read with `appTexts.text(key, params)`;  each other language is a LAZY `AppTexts.<lang>.ts` beside it,
    with every key (its type says so)
  - the language server (`spell/app/lsp`):  its labels are keys in `LspTexts.en.ts`,
    read in the language of the FILE they're about (`LSP.LspTexts.of(scope)`)
  - A sentence that names something takes it as a param (`{type}`, `{theType}`), never glued from pieces:
    each language words it its own way.
  - NOT:  a `MSG.ts` of every string in a package that speaks only English -- one more file to keep in step, for no
    localization.
  • An AGENTS.md section that shares a WWOD rule's name EXTENDS it. Its first line says so, "As WWOD §12, plus:", then gives only what's local.
  • Today 20 of the kit's AGENTS.md files do it, most for §4 (imports), §8 (the folder's namespace) and §12 (classes).
  • NOT: under a rule records the option chosen AGAINST, with the why, so nobody proposes it again: #private, a MSG.ts per package.
  • Each spoke opens with a From: line naming where its rules came from. Those lines cite the ORIGINAL numbers, so the check skips them.
  • The one rule a project chooses. In Spell the source is the spec: a test that disagrees with the code is rewritten to match it, unless the code is obviously wrong.
  • And the report names each test rewritten that way, with why the old expectation was wrong.
  • It's the opposite of test-first, where a failing test comes first and the tests are the spec. So it's its own file, read only by a project that opts in, and says so in its AGENTS.md.
  • Without it, WWOD §1 says only that tests follow the project's own way. A project that says nothing: an agent follows its tests as they are, and asks before rewriting one.
  1. Put it in the spoke for its topic, or in the hub if every task needs it, as a bullet with a bold title.
  2. A rule chosen against: a NOT: line under the winning rule, with the why.
  3. Cite real code by its repo path, so an agent can read the example.
  4. A new section is numbered after the last.
  5. Then spell wwod check.
  • Move a rule, never copy it. Leave a SEE: line where it was.
  • Code that doesn't follow a new rule yet gets an entry in the code-debt log, not a silent rewrite.

spell wwod check resolves every citation and backticked repo path in WWOD, every AGENTS.md and CLAUDE.md, the Solid 2 rules and the skills, and exits 1 on a broken one.

spell wwod check, at the kit's root, its last line · 1 line 
18 files, 21 sections, 242 rules, 112 problems
  • Every WWOD §N must name a section, and every WWOD §N › "title" a rule in it.
  • A skill is checked for its citations only: its paths are relative to the skill.
  • A new file that starts citing WWOD must be added to the check's list (CITERS, in wwod.ts), or the check never reads it, and never says so.
  • Not yet: over a hundred of WWOD's example lines still cite files by paths from before the repos were one (packages/...), and the check lists each one.
a project that installs spell · 1 line 
npx spell@next wwod init
  • Three questions: WWOD, the Solid 2 rules, and §21. Then the rules' lines go in your CLAUDE.md (an @ line each) and AGENTS.md (the same, in plain words).
  • Each file's lines sit in one marked block: run it again to add or drop a rule.
  • --yes with --solid, --code-is-the-spec or --no-wwod asks nothing; --dry-run writes nothing.
  • The package ships agents/wwod and agents/solid only: the logs and the coherence catalog are Spell's own.
  • The edge: WWOD's examples cite Spell's own files; read them as illustrations. A rule in your own AGENTS.md wins where it disagrees.

Problems known and lived with go in three logs, each with a ## <folder> section per folder and its own rules in its header. WWOD §1 › "Record deviations and known issues; NEVER fix them silently" sends agents there.

  • Code debt: structural debt chosen not to fix yet, including code that doesn't follow a WWOD rule yet.
  • Suspected bugs: looks like a bug, not sure yet.
  • Papercuts: anything that slowed development down; check it first when tooling fails.
  • They're Spell's own, kept in the epic folder, one copy for every checkout: the kit's agents/ holds links to them. Edit them at their real path, never through the link.
  • Rules, not a linter: nothing but review holds code to most of them.
  • Stale example paths: over a hundred, listed by spell wwod check (above).
  • The plugin is Claude Code's: the Markdown works for any agent, but the skills and hooks around it are Claude Code's for now.
  • The rules are long: about 19k tokens with the Solid 2 rules, which is why only the hub loads by itself.
