How the Parser Works

 
print the first card of the deck is face up
core.console.log(core.getItemAt(deck, 0)?.isFaceUp)

The card is face up, not the deck. A parser that guessed from the shape of the line would get that wrong, and an early one did. This page is how Spell's parser gets it right: how tightly each word binds, which rule wins a tie, how a program teaches the parser its own words, and how every match knows what it IS.

Written for: anyone about to change the parser's rules, or wondering why a line read the way it did Checked: 2026-11-21, every output on this page printed by spell parse on that day's code The reference beside it: the parser's README, README-parser, and the deep map, PARSING.md
  • The parser knows no language until rules are registered on it.
    • A rule is a class, plus a syntax string in Rulex, which reads like a regular expression over words.
    • No grammar file, no generator, nothing generated to check in.
    • Spell is written on it, and so is GitHub markdown.
  • A line goes through six stages: tokens, rules, matches, the Spell tree, output, running it. README-parser follows one line through all six.
  • Two numbers decide how a line reads, and they answer different questions:
    • precedence: how tightly an operator holds its operands (* before +)
    • priority: of several rules matching the same words, which one wins
  • Scope is what the program has declared so far. A line that declares something adds words, even whole rules, for the lines after it.
  • Every match has a datatype, in Spell's words: text, Card, list of cards. Calls use it to pick the right method.
  • The same text gives the same tree, every time. A line nothing understands stays a parse error, and the rest still parses.

In a parser generator you'd write a grammar level per operator. Here there's ONE rule for every expression, and a table of numbers says how the operators group.

  • CompoundExpression is THE expression rule: {lhs:operand} {rhsChain:expression_suffix}*.
    • It reads one operand, then each suffix that binds tighter than its bound (0: all of them).
    • No suffix: it hands back the operand's own match, so a rule can still ask what kind of thing it got.
  • An operand is what an operator acts on: 5, the deck, (x + 1).
    • Every rule aliased expression, but this one, is registered as an operand instead.
    • Operands nest: the first card of the deck holds the deck.
    • An operand whose syntax STARTS with an expression throws when it registers: it would call itself forever. Something that follows an expression is a suffix instead.
  • Each suffix's right side is an operand, so the chain comes out flat, as above. getAST() then groups it by precedence, a shunting-yard over the chain.
  • A postfix groups like an infix: x + y is empty compiles to core.isEmpty(x + y).

Every operator suffix takes its precedence from this table, in expressions.shared.ts. Its constructor throws without one: a silent default is how ends with once went wrong.

print the absolute value of x + 1 is 3 core.absoluteValue(x + 1) === 3
print the number of items in names + 1 core.itemCountOf(names) + 1
print "Total:" && x + 1 core.joined("Total:", x + 1, " ")
print x is 1 and y is 2 or z is 3 (x === 1 && y === 2) || z === 3

The catch: math prefixes like the absolute value of take the whole sum, while list prefixes like the number of take one operand. Each reads naturally, but they differ on purpose.

  • As a STATEMENT, a method call takes whole expressions: notify x + y compiles to notifyMessage(x + y).
  • INSIDE an expression, its last slot is an operand: if double x is 4 compiles to if (doubleN(x) === 4).
  • One flag does it, operandInExpressions: registering the statement registers an operand twin, its last {x:expression} made {x:operand}.
  • A project's declarations still write ONE rule: loading it makes both.

The parser doesn't backtrack, with one exception: a required word that fails right after a {slot} makes the slot give back what it took. 

remove the card of the pile            rule:  remove {thisArg:expression} of {callArgs:expression}
{thisArg} takes "the card of the pile" (a property read)   ->  needs the word `of`:  none left
give back:  re-parse {thisArg} cut before the last `of` it took  ->  "the card", and `of` fits
{callArgs} = "the pile"   ->  card.removeOfPile(pile)
  • Sequence.giveBack(), tried only on the way to failing, so whatever parsed before still parses the same.
  • Never while completing a line in the editor (expecting mode).

A Choice tries every alternative that can start with the line's first word, then keeps:

  1. the highest priority: only between rules matching the same words
  2. then the longest match
  3. then the one registered first

Nothing reports a tie: the earlier rule just wins. So the order of a module's registration file, <module>.en.ts, is part of the grammar.

a card has a direction as either up or down
a card "is face up" if its direction is up
  • The third line declares an alias, and the alias becomes a RULE while it parses: {operator:is_or_is_not} face up. So the card is not face up reads too.
  • Only a rule's mutateScope() changes scope. Building the Spell tree never does, nor looks scope up.
  • A rule that needs something from scope looks it up WHILE PARSING, into match.data: a member, a list's item type, a method's record.
  • Every type and method a project declares is stubbed before its files parse, so a line can use one declared further down.
  • An alias can't be used above its definition yet: spell lint says Don't understand "is face up".
  • The editor re-parses only what an edit could change; every scope change is journaled, so a rewind is cheap.

Binding gets the shape right. Knowing what an expression IS gets the meaning right: the length of title is title.length, while the length of the deck is core.itemCountOf(deck).

  • match.datatype remembers rule.getDatatype(match); its default is the rule's datatype.
  • About a dozen rules work it out, reading only match.data and their child matches.
  • Unknown is undefined, and fits everything: nothing stops parsing for want of a type.
  • The first datatype wins: a variable's is set when it's declared, never widened. Except a getter's property and a method's return type, set once the body has parsed.
  • One normaliser, SP.typeName(), turns what people write (string, yes or no, plurals) into Spell's words.
  • literals, from their rule: [1, 2, 3] is a list of numbers
  • a variable, from its scope record
  • a new card is a Card; a new list of cards a list of cards
  • the X of Y and its X, from the member found on Y's type; a built-in's from its table
  • a method call, from what its method returns: every return agreeing, else unknown; a bare return is nothing
  • comparisons, aliases, and, or, not: choice
  • - * /: number; + of text: text
  • a whole expression: the same shunting-yard as its tree, over each suffix's result
  • a new variable, from set, get or X is Y
  • method arguments: (a card), (x as text)
  • it inside a method or getter: its owner type
  • a loop's item, and a where's: the list's item type
  • a deck is a list of cards: Card, as the deck type's item type
  • A call rule is made for its method with that method's types: who owns it, and each parameter's.
  • It refuses a match whose argument's datatype is KNOWN and can't be the parameter's. Unknown always fits.
    • put the chip on the pot finds the chip's put.
    • add the card to the deck falls past a project's to add a card to a pile, to the built-in.
  • A project that imports another gets the same types: each declaration's marker comment carries them.
  • The built-in types live in the root scope, in BUILT_IN_TYPES: text, number, integer, letter, choice, date, list, thing, view, page, app, place, dimension, nothing, and more.
  • Their members are DATA, SP.BUILT_IN_TYPE_TABLE in builtinTypes.ts: each entry's docs, item type (text holds letters) and members.
  • A project's own declaration wins over the table.
  • The Type Explorer builds the built-ins from it, and yarn lsp:scopes, in the app folder, writes the core's core.scopes.js from it.

Binding and datatypes are what let Spell read signatures without parentheses, typed calls, members of several words (the short rank of the card), membership and list guards. How each one is written: The Spell Language. How each one is parsed: PARSING.md, "Members" and "Guards".

Every rule's syntax is Rulex, read ONCE when the rule registers. A bad syntax fails at load, naming the part it couldn't read. The traps left are the ones that do something you didn't mean:

  • Two tokenizers. Rulex reads each syntax with its own plain one, so --, //, #, quotes and <tag> are ordinary symbols in a syntax. The LANGUAGE's tokenizer decides what they are in the input: Spell's makes -- a comment, and no rule ever sees it.
  • * is Rulex's own: **{text}** is a repeat flag, so write \*\*{word}\*\*.
  • Touching in the syntax means touching in the input; a space in the syntax allows one but doesn't require it.
  • A bare [, { or ( only ever OPENS a list, a rule or a choice. A literal one is \[.
  • A rule may name itself, but not FIRST: ({sum} plus {num}|{num}) calls itself forever, and dies with "Maximum call stack size exceeded". Write {num} (plus {num})*, or use the precedence table.
  • Printing a rule back (spell explain) loses what the rule doesn't keep: redundant parentheses, and the escapes in a choice of symbols.

  • GitHub markdown on the same parser, which never imports Spell: it passes all 670 of the spec's examples.
  • Rulex says what each LINE is; nesting and emphasis pairing are hand-written code, ported from commonmark.js.
  • The editor's docstrings, <spell-markdown> and the language server draw with it.

How it's built, and how it was measured: README-markdown.

  • Nothing reports a tie between two rules matching the same words equally well: the first registered wins.
  • Spell has no expression statement: a bare the first letter of name as upper case on its own line is a parse error.
  • A typed parameter turns away a literal of the wrong type: with to notify (message as text), notify 1 falls to the built-in core.notify(1).
  • A member of several words needs its owner's type: the short rank of x, with x of no known type, is a parse error.
  • Datatypes are still unknown in places, and unknown fits everything: a mis-parse that compiles is caught only by the tests.
  • An alias can't be used above the line that makes it.
