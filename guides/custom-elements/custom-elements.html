Custom Elements

Click +1 on the <ui-counter max="5"> in section 4 five times. The tag gains a count="5" attribute, a count property, and a :state(at-max) for CSS, and its button turns off. It is four small files, 215 lines in all, built step by step on this page.

That's how every <ui-*> element works. A React component is a function the framework calls, and the page never holds it; a <ui-button> is a node the page holds, like <video>. Below: how one works from the browser's side and from ours, for anyone about to write or change a Spell UI component, new to custom elements or not.

Written for: whoever writes Spell UI components, or elements of their own on the same base; no custom-element knowledge assumed Checked: 2026-11-21, every code block against the file it names, the counter rebuilt that day The reference beside it: README/element, the element base in full

Every Spell UI tag (<ui-button>, <ui-select> ...) is a custom element: a tag of our own, which the browser runs like one of its own. So are the epic pages' tags, and every view a Spell program draws.

  • Behind each tag are TWO objects (see Two objects per tag):
    • the DOM element in the page, a DOMElement
    • its component, a UIComponent subclass (UIButton), which holds the state and draws the element's inside
  • A component is a class, with:
    • decorators that say how each member works (@E.state, @E.controlled ...)
    • hooks it fills in (render(), onConnect() ...)
  • A lint guard keeps component files on the decorators: it flags an effect, listener or timer written by hand.
  • The components draw with Solid 2; this guide only says what's ours, and links Solid's own rules.
  • This page is the tutorial. The reference, every decorator and hook, is README/element.
  • New to custom elements: read 2. The platform first, then build the counter in 4.
  • Writing a component today: 5. A real one, then the reference (7).
  • The live examples are real elements: click them, and their inspector beside them shows what changed.
  • Solid's rules (no writes while drawing, effects in two halves): Solid 2 in Spell. The short form for agents: ui's AGENTS.md, "Solid authoring".

What the browser gives every custom element, each in a sentence or two, with where to read more. Spell UI uses all of it.

  • A custom element is a tag with a dash in its name, backed by a class that extends HTMLElement.
  • customElements.define("ui-button", Class) registers it.
    • A tag already in the page before that is an ordinary element until then.
    • Defining it upgrades every one of them in place.
  • A tag can be defined only ONCE per page.
  • MDN: Using custom elements, customElements.define()
  • The browser calls methods of the class as things happen: connectedCallback() when the element is added to a page, disconnectedCallback() when it's removed.
  • A move (re-parenting, sorting a list) is a disconnect, then a connect: the object itself stays the same.
  • MDN: Custom element lifecycle callbacks
  • A static observedAttributes list names the attributes the class wants to hear about.
  • The browser then calls attributeChangedCallback(name, old, new) on every change of one, with the TEXT (or null, removed).
  • It reads the list once, when the tag is defined.
  • MDN: Responding to attribute changes
  • A shadow root is a private tree inside the element: the page's CSS and querySelector() don't reach in, and its CSS doesn't leak out.
    • Every Spell UI element draws into one.
  • The element's own children (its light DOM) show where the shadow tree has a <slot>; slot="icon" on a child picks a named slot.
  • part="button" on a shadow node lets a page style it from outside: ui-button::part(button).
  • MDN: Using shadow DOM, <slot>, ::part()
  • A shadow root can share one CSSStyleSheet object with every other root (root.adoptedStyleSheets = [sheet]): 1,000 buttons, one parsed sheet.
  • The runtime makes each component sheet once (UI.styles), and each element adopts it.
  • MDN: ShadowRoot.adoptedStyleSheets
  • attachInternals() hands the class a private object for things only the element itself should set: its default ARIA role and states, its custom states, and its form value.
  • ARIA set there (internals.role = "group") is a DEFAULT: an aria-* attribute the page writes still wins.
  • MDN: ElementInternals
  • internals.states.add("active") puts the element in a state CSS can select: ui-button:state(active).
  • Like :checked for a checkbox: it isn't an attribute, so the page's markup stays as written.
  • MDN: CustomStateSet, :state()
  • A class with static formAssociated = true takes part in its form, as an input does:
    • it submits a value (internals.setFormValue())
    • it has validity
    • it's reset with the form
  • The browser reports form events through more callbacks:
    • formAssociatedCallback()
    • formDisabledCallback()
    • formResetCallback()
    • formStateRestoreCallback()
  • MDN: ElementInternals.setFormValue(), ElementInternals.form
  • An event made with composed: true leaves the shadow root; outside, its target is the element itself (it's retargeted), not the inner node.
  • Spell UI's own events (ui-change ...) are CustomEvents that bubble and are composed.
  • MDN: Event.composed, CustomEvent
  • <template shadowrootmode="open"> in HTML makes a shadow root as the page parses, before any script runs.
  • An element that finds one already there draws into it (see The static render).
  • MDN: <template shadowrootmode>

Each <ui-button> in a page is TWO objects that point at each other.

  • The <ui-button> in the page is an instance of DOMElement.
    • The same way, an <a> is an HTMLAnchorElement.
  • It's the browser's side:
    • the DOM API callbacks
    • a property per attribute (button.size = "large")
    • the converted values (attributeValues)
    • internals
    • the shadow root (renderRoot)
    • the ready promise
  • Each tag gets its OWN subclass, made by define(), carrying that tag's tagSetup.
  • A family that adds script API names its own subclass (see Patterns that repeat).
    • <ui-include>'s is DOMIncludeElement. It adds contentRoot.
  • One instance per element of its UIComponent subclass:
    • built the first time the element connects
    • kept across moves, until domElement.dispose()
  • It holds the state, draws the shadow DOM with render(), and handles the events.
  • It reads every attribute as a getter, converted and typed: this.size, this.toggle.
  • It draws inside a Solid root of its OWN: a Solid app's context doesn't reach in (appContext does that).
  • UIButton.en.ts names EVERYTHING the tag uses: its tag, attributes (and how each converts), events, slots, parts, states and texts.
  • Code never writes those names as strings: it reads them through the vocabulary, so a translated tag (<ie-boton primario>) runs the same code.
  • define() builds an ElementDefinition from it for the actual tag: each attribute's attribute name, property name and canonical key, and the converters.
  • The vocabulary also gives:
    • the tag's topics and aka: how people look for it
    • its skeleton: what <ui-root display="skeleton"> draws

A family's index.ts calls UIButton.define() as it loads. In order, it:

  1. builds the definition
  2. records it for the page
  3. makes the tag's DOM element class
  4. hands it to the browser
UIComponent.define() · UIComponent.tsx · 13 lines 
static define(this: E.UIComponentClass, tag?: string, dictionary?: E.Dictionary): CustomElementConstructor {
  const definition = new E.ElementDefinition(this.prototype.vocabulary, { tag, dictionary })
  const existing = customElements.get(definition.tag)
  if (existing) return existing
  // record it, make the tag's own DOM element class on `elementSetup.DOMElement`, and define it (DOM API)
  UIComponent.register.call(this, definition)
  const Class = DOMElement.subclassForTag(
    this.prototype.elementSetup.DOMElement,
    UIComponent.tagSetupFor(this, definition)
  )
  customElements.define(definition.tag, Class)
  return Class
}
 4. Build one: <ui-counter>

A small element, written step by step: a number, and a button that adds step to it, up to max. It's no mock-up: the counter below is built from these files.

Clicks
  • Click +1 (or focus it and press + or ↑): count appears as an attribute and a property.
    • At 5, :state(at-max) comes in and the button turns off.
  • Its files: ui-counter/, beside this guide.
    • It's a GUIDE-ONLY element: not part of Spell UI, its site or its bundles.
  • Every name the tag uses, in one object: the tag, its attributes (each with a kind, which says how its text converts), its event, slot, parts, state and text.
  • count has no default: left out, it's undefined, and the counter keeps its own number (step 3).
  • step's default is 1.
  • size is a kind: "size" attribute: it adds its word to the class, in Fomantic's class grammar ("ui large counter").
  • as const satisfies E.ComponentVocabulary: the shape is checked, and every name stays a literal type, so this.partForName("buton") fails TypeScript.

    • Everything shared comes from spell/ui/core, imported as E.

Adding · UICounter.tsx · 6 lines 
@E.untracked
add(originalEvent: Event) {
  if (this.isAtMax) return
  const next = Math.min(this.currentCount + this.step!, this.max ?? Infinity)
  this.requestChange("currentCount", next, () => this.send("ui-change", { count: next, originalEvent }))
}

protected classValue(name: E.AttributeName<typeof buttonVocabulary>): unknown {
  if (name === "selected") return this.isActive
  if (name === "disabled") return this.isDisabled
  if (name === "labeled" && this.hasBadge) return false
  return super.classValue(name)
}

/** `icon` for icon-only buttons and for `labeled icon` buttons. */
protected get extraClass(): string | undefined {
  if (!this.hasIcon || this.reveal) return undefined
  const isLabeledIcon = !!this.labeled && !this.hasBadge
  return !this.hasText || isLabeledIcon ? UIT.ICON_CLASS : undefined
}

The click handler · UIButton.tsx · 18 lines 
private readonly onClick = (event: MouseEvent) => {
  if (this.isDisabled) {
    event.preventDefault()
    return
  }
  this.resolveInvoker()
  this.runInvoker(event)
  if (this.toggle) {
    const next = !this.isActive
    this.requestChange("isActive", next, () =>
      this.send(next ? "ui-selected" : "ui-deselected", { active: next, originalEvent: event })
    )
  }
  const { form } = this.domElement.internals
  if (!form) return
  if (this.type === "submit") this.submit(form)
  else if (this.type === "reset") form.reset()
}

Spell UI follows the house style everywhere but a few places, and most of those have one reason: a component library ships every byte to every page.

  • A module constant, not a private static: one under a class minifies to one letter, and a static keeps its name. Moving them to statics cost forms.js 0.27 kB gzipped, when it was tried.
  • Fomantic's class grammar stays: ui small basic primary button is what the sheets key on, so rootClass writes it from the attributes.
  • Vocabularies are data, which node loads without a DOM: the components page, the static render, the property editor and the Spanish tags all read them.
  • Two objects per tag, so the browser's side (attributes, internals, the shadow root) and Solid's side (state, drawing) each stay in one place.
  • Changing values are fields with a decorator, read fresh right after a write, never a signal pair written by hand.
  • Each exception, and the rule it departs from: ui's AGENTS.md, where a section named like a house-style rule starts "As WWOD §N, plus:".

What's left of how an element works, a line or two each. The whole of it is README/element, and each class's own docstring in src/element/.

  • Standard (TC39) decorators, most in Reactive.ts: @E.state, @E.controlled, @E.derived, @E.cssState, @E.aria, @E.onChange, @E.whileConnected, @E.watches, @E.on, @E.untracked.
  • @E.proto and @E.protoMerged set class settings once, on the prototype.
  • The lint guard fails a hand-written effect, observer, listener, untrack() or timer in a component file: "The lint guard" in ui's AGENTS.md.
  • README/element: "It renders once, and a write reaches only what read it".
  • define(), then the DOM element's constructor; on its first connect, mount() builds the component, then onMount() and render(), then onConnect().
  • A disconnect calls onDisconnect() and keeps the component; a reconnect calls onConnect() again.
  • dispose() releases the component and its listeners.
  • The hooks' docstrings: UIComponent.tsx.
  • size="large" or button.size = "large" converts through the tag's ElementDefinition and is stored in attributeValues.
  • A property write is written back to the attribute.
  • The component's getter, this.size, reads the new value, and only what read it redraws.
  • this.send("ui-change", { ... }) sends the vocabulary's event from the DOM element: it bubbles, and leaves the shadow root.
  • Cancelable when the vocabulary says so: then it returns false if a listener called preventDefault().
  • @E.on("keydown") listens on the DOM element for its whole life; a translated tag sends and hears its own names.
  • Through the timing helpers, never the platform's calls, so the code says WHEN it runs: afterSolidUpdate(), after(), waitUntil() ...
  • They're spell/util/timing's, re-exported as E's.
  • The generic parts (<ui-header>, <ui-content> ...) are ONE element each, wherever they sit.
  • A header in a card climbs to its owner and says so with :state(in-card); the climb stops at a component that isn't a part.
  • A form control extends F.FormComponent, from spell/ui/forms: its DOM element is a DOMFormControl, with form, validity and checkValidity().
  • A tag that shows a text file extends LoadableComponent: source, inline text, save().
  • A family with a script API of its own names its own DOM element class: <ui-include>'s adds contentRoot.
  • Every element takes disabled, loading, visible (or hidden) and animation, though its vocabulary never names them, and the platform's inert.
  • README/element: "What every element gets without asking".
  • Each element draws inside an error boundary of its own. When it throws, it gets :state(errored), one console error names the tag, and it sends a cancelable ui-error.
  • Then it shows its fallback: a form control's plain native one, else a bare slot, so its children still show.
  • In development, an edit to a component swaps it into every live element, which redraws keeping its attributes and properties; an edit to its CSS swaps the sheet with no redraw.
  • What the browser reads only once (the observed attributes, form association) reloads the page instead: HotDefinitions.ts.
  • A page of ui-* elements as plain HTML, for search engines and readers with no JavaScript: spell ssr.
  • Only @E.aria members and @E.onChange(..., { writesDOMElement: true }) methods run there.
