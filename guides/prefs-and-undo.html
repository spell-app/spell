What Compiled Spell Runs On

 
a "card" is a thing where:
	- its "direction" is either up or down
	- to "turn over", undoable as "Turn Card":
		set its direction to down
What spell parse compiled it to, its end 
  turnOver() {
    this.direction = "down"
  }
}
core.describeAction(Card, "turnOver", { title: "Turn Over", undoneAs: "Turn Card" })

That last line is all it takes for ⌘Z to put the card back. The undo history, the defaults, the card's own element on the page and the game kept across an edit are the RUNTIME's: core, the one object every compiled program imports. This page is what it does for a program, and how.

Written for: anyone changing the core, giving a program undo, or reading compiled Spell Checked: 2026-11-21, every output on this page printed by that day's code The reference beside it: README-core, and the kit's helpers under it, README/util
  • Compiled JavaScript imports one name, @spell/core: an object of helpers, and the classes a program's types extend (Thing, List, App, View, ViewableList).
  • An unset property reads a default by its type: its first choice, 0, empty text, no.
  • Every action is one undo step by itself. Undo runs nothing backwards: it puts each prop back.
  • A prop declared remembered keeps its value from run to run, in the person's preferences.
  • A view gets its own custom element, <solitaire-card>, whose attributes and its thing always agree.
  • An edit in the editor keeps the game in progress: the things carry over, and the start doesn't run again.
  • Every running app gets a core of its own.
 
import { core, Thing, List, App, View, ViewableList } from "@spell/core"
  • @spell/core isn't a package you install. Whatever runs the program points it at a copy of the core: the page's runner, or node's module hooks under spell run.
  • Each writer uses the language's own word where it has one, the core only where it doesn't: JavaScript has no range that includes its end, so core.getRange(1, 100); Python writes range(1, 101).
  • The core is assembled as it loads: each module adds its helpers to the one object. Its pieces, and where each is: README-core, "The pieces".
  • Python's twin is spell_core: Targets.
  • An unset property reads its declared default, else its first choice, else its type's own: 0 for a number, empty text, no for a choice.
  • So a card made with no suit is a club, and black.
  • The default is never stored: the card's JSON leaves it out, and its element has no suit attribute.
  • spell_core reads the same defaults.

An editor's undo usually runs a command backwards. This one runs nothing: a step keeps each prop's value before its first change and after its last, and each list's items, and undo sets them back.

Spell says The step
to "turn over": one step, named by its title: "Undo Turn Over"
to "turn over", undoable as "Turn Card": one step, "Undo Turn Card"
to "give a hint", can't be undone: no step; the steps before it are kept
a question (gives back yes or no), a drawing, a test never a step
  • The same words go on a line indented under the action instead: undoable as "Turn Card".
  • On a type it compiles to core.describeAction(...); at the top level, the action runs inside core.asAction(...).
  • What another action calls joins that action's step. A deal that waits between cards is ONE step, and its redo is instant.
  • Each run has one history, of at most 100 steps; loading saved state clears it.
  • The app has undo(), redo(), and live canUndo, undoTitle, in the program's language. ⌘Z and ⇧⌘Z work while the app has the focus; a text field and a modal keep their own.
  • The catch: nothing undoes while an action still runs, so ⌘Z mid-deal waits for the deal to finish.
await history.transaction("Deal", async () => {
  for (const margin of [10, 20, 30]) {
    await Promise.resolve() // a wait:  what comes after it still joins "Deal"
    setMargin(margin)
  }
})
history.undoTitle   // "Undo Deal":  three changes, one step
history.undo()      // margin 0, at once
history.redo()      // margin 30, at once:  nothing runs again
  • The generic part is the kit's UndoStack: a step is a title and its records, each saying how to undo and redo itself.
  • A transaction stays open until its function returns or its promise settles: anything recorded meanwhile joins it.
  • A run of steps with the same title AND target folds into one: typing "hello" into a field undoes in one go.
  • Its titles read Spell cells, so a menu reading them redraws by itself.
  • Every method: README/util, "UndoStack".
  • The core's history, undoing.ts, hears each prop set and each list's items changed while an action runs.
  • A prop declared undoable: false, a selection say, is left out of every step.
  • While it undoes or redoes, nothing records, so what it puts back isn't a new step.
  • Python's spell_core keeps the same history, in undoing.py.

await core.remember("@local/solitaire")
new Solitaire().theme          // "light", its first choice
new Solitaire().theme = "dark" // kept under @local/solitaire:theme
// the next run:  remember() again, and it's "dark"
  • Whoever runs the program calls core.remember() with the project's id first. The editor and <spell-viewer> do; spell run and the tests don't, and there a remembered prop is a plain one.
  • An app's prop is kept by its name; any other thing's under the id the program gave it. A thing with a made-up id gets a new one each run, so its prop isn't kept, and the console says so once.
  • Only text, numbers and choices. A kept value the prop no longer allows starts afresh.
  • Not yet: Spell has no words for it, so a program's own TypeScript declares it, as the core's tests do. And spell_core remembers nothing. 
const prefs = new PrefStore("spell-site").declare("scheme", { oneOf: ["light", "dark", "auto"] })
prefs.get("scheme")            // "light":  nothing kept yet, so the first choice
prefs.set("scheme", "dark")    // localStorage now holds  spell-site:scheme = dark
  • Remembered props are kept in a PrefStore named for the project's id.
  • Every key starts with the store's name and a colon; every value is text people and plain scripts can read.
  • It never throws when storage fails: blocked storage keeps values in memory for the visit, and says so once.
  • The browser's storage, unless the runner names another place.
  • Two places must be waited on: the browser's database, and the page server's /api/prefs, in the person's space, so a preference follows them.
  • The core reads them whole as the run starts, so after that they answer at once.
  • A place decides WHERE a value goes, never how it's asked for: the code that asks never changes.

A type declared a view draws as its own custom element, so the browser's inspector says which thing each one is.

  • The class names its tag as it's declared: static elementTag = core.defineElement(this, "Solitaire").
  • The tag is the project's name, then the type's, in dashed lowercase: Solitaire and Card make <solitaire-card>; games and BankAccount, <games-bank-account>. An app's is <solitaire-app>.
  • The core only NAMES the tag. The page defines it, on SpellElement, because the core may not import Solid or Spell UI.
  • The element draws its thing's own to draw in its shadow root, in an error boundary of its own: a card that fails shows its own stand-in, and the rest keep drawing.
  • Each declared property is an attribute, kebab-cased, and an element property, camelCased: face up is face-up and faceUp.
  • Each method is an element method calling the thing's: card.turnOver().
  • A property holding another thing shows as its reference: pile="Tableau#T1". A list is an element property only.
  • The tag and its thing agree both ways: turning the card over changes direction, and setting the attribute changes the card, which redraws.
  • The id is the thing's name; two of one name are numbered, queen-of-spades-2. A space is a dash.
  • A tag written by hand finds its thing by its id (<solitaire-tableau id="T1">), or, with no id, as the program's one thing of that type.
  • Compiled TypeScript writes, after each view, its element class: class CardElement extends SpellElement<Card>, with its attributes, its sheet, and one method per method of the type.
  • It never defines the tag itself: core.useElement(Card, CardElement) hands the class to the page.
  • Its base comes from a name of its own, @spell/elements: the app's real element for the type check, the runtime's on a page, a stand-in that makes no element in a headless run.

Edit a card's CSS in the editor mid-game, and the game stays where it was, drawn in the new colour. Fast Refresh keeps a component's state; this keeps what the program MADE.

  1. The new program loads with its start skipped: its types, functions and top-level things are made, its tests and its app's start aren't.
  2. Each top-level thing of the last run, matched by name and type, is copied into the new run's, as the new classes. A card held by the deck and a pile stays one card.
  3. The console says so: Kept allPiles, deck, ... from the last run: Restart starts afresh.

  • A program's START is its top-level test calls and the line starting its app; the compiler marks each, at a file's top level only.
  • Every other top-level line still runs on an edit, a print included.
  • A property added gets the new thing's own starting value; one removed is dropped.
  • It starts afresh, as Restart does, when the edit changed the file that starts the app, added or removed a file, or changed a property's type or renamed a type. The console says why.
  • Restart starts afresh on purpose: <spell-viewer>'s, the editor's and VS Code's.
  • A first run, spell run and the core contract always run the whole program.
  • A program's things, console, listeners and undo history live in its core, so every running app gets its own.
  • In a page, only the app folder's runner imports the core's code, bundled as spell-runtime.js; each <spell-viewer> imports a fresh copy, from a blob: address of its own.
  • Everything else, the editor and the parser among them, imports only the core's TYPES, which erase to nothing.
  • spell/parser/core/model is the one other entry: the core without drawing, for libraries and the server.
  • The core never touches document: an app runs in a shadow root, core.appRoot.
  • Remembered props have no Spell words yet, and spell_core keeps none.
  • Nothing undoes while an undoable action still runs.
  • A Python program never carries things over: thing references and element classes aren't in its runtime yet.
  • A plain top-level variable, a number or a text, starts again from the new start.
  • A tag's attributes and methods are fixed the first time it's defined: one an edit adds needs a reload.
