The spell Command

 spell lint, on a project whose last line Spell can't read · 4 lines 
$ spell lint Hello
✗ @local/clihook/Hello  1 error · 1 warning
Hello/Hello.spell:4:1  Don't understand "print greeting"
$ echo $?
1

That's the same error the editor underlines, because spell loads projects the way the language server does. One command over every folder of the kit: if you've used git or cargo, you know the shape, a verb after it and --help on everything.

What's different is where the verbs come from: each folder names its own in its package.json, and spell --help lists them under the folder that added them. And there's no build step: in a checkout, spell runs your source through tsx, so the next run runs your edit.

Written for: anyone running Spell projects from a terminal, or adding a command Checked: 2026-11-21, every command against spell --help and its own help that day The reference beside it, with every verb and flag: the command-line README
  • Set it up once: yarn cli:install at the kit's root links bin/spell.mjs onto your PATH. It's a link, so a git pull is an upgrade.
  • The parser folder's commands compile, lint, run, test, format, explain and translate Spell projects.
  • The repo tools go by noun, then verb: spell server start, spell pack build, spell runbook start.
  • epic is the other command you'll type: epic pages, worktrees, windows, reviews. It's the epic folder's, with its own verbs.
  • Output goes to stdout; progress and screens go to stderr.
  • Exit codes: 0 fine; 1 the Spell has errors, or a test failed; 2 the command line is wrong.

Every project command takes the same kinds of target:

  • a .spell file, or a project folder (one with a __project.json5)
  • @here: the project in the current folder
  • a project by its address: @spell/examples/fizzbuzz
  • a file in one: its name has a dot
  • a group, @spell/examples: pick from its projects, or --all takes them all
  • none: the project here, or, outside one, a prompt that completes as you type
  • spell projects lists the groups; spell projects <group>, its projects.
  • --verbose, on any command, shows Spell's own logging on stderr.
command what it does
compile writes <Project>.spell.js, and each *.editor.html's module; --target for another writer, --stdout to print it
lint errors, one a line as path:line:col, exit 1 if any; --fix rewrites old forms
upgrade brings a project written for an older Spell up to date, then records its Spell version
run compiles and runs a project; one with a UI opens in your browser, until Ctrl-C
test runs each to test ..., reporting ✓ or ✗; exit 1 if any fail
watch recompiles as files change, showing errors, until q or Ctrl-C
format tidies a .spell file's whitespace, as VS Code's Format Document does
describe what a file or project declares, as the Type Explorer shows it, or all about one thing
parse, repl how Spell reads a line: its match tree, then the JavaScript it compiles to
explain what a word means to Spell: the rules it names or starts
speedtest times the parser's rule tests; --against HEAD compares with a commit
translate writes a project in another language: its names, then line by line, then Claude fixes each line that fails a check
place the places a program's data lives in: look at a source, sign in, check its reference page
  • compile writes the targets the project file names; --target ts/solid adds one. spell run <project> --target py runs it as Python.
  • The catch: their work is the app folder's for now, through its language hook. In a clone the app folder is always there; without it, each stops and exits 2.

The base is the kit's src/cli/: it reads the arguments, prints the help, and finds the commands. Each folder hands it a list, named in its own package.json.

a folder's package.json · 1 line 
"spell": { "commands": "./src/cli/commands.ts" }
  • It reads the root's package.json, then each folder's, lowest first: parser/, ui/, epic/, app/.
  • A word two folders both add goes under each one's short name, and the bare word only says where they went. No two clash today.
  • A folder can plug work into a lower one's commands, by hook: the app's language hook does the parser's commands' work.
  • Adding a command: read the commands guide first, then keep the commands page true with spell commands check.
  • The link runs the checkout it was made from. Run from inside another checkout of the kit (an epic's worktree), it hands off to that checkout's own bin/spell.mjs, so the worktree's code runs.
  • In a project that installs spell from npm, and runs no checkout, it hands off to the project's own install.
  • The first run takes a few seconds, while tsx compiles the source and caches it. After that the base answers in about 0.1 s, and a language command in about one.
  • The language commands need the app folder: moving their work down into the parser is still to come.
  • The repo checks aren't spell commands: yarn ts, yarn test and the rest are yarn scripts; spell lint and spell format are for .spell programs.
  • No command starts the language server yet: the VS Code extension starts the language server by its file, with tsx.
