Working on Spell

 a change from branch to merged, in an epic's worktree · 8 steps 
# 1.  A branch of the whole repo:  in Claude Code, /isolate readme (or /epic readme)
cd ~/www/spell.worktrees/readme

# 2.  Edit, then run the tests you're near:  here, the server's router
yarn vp test run Router
#  Test Files  1 passed (1)
#       Tests  21 passed (21)

# 3.  The finishing pass:  ts, lint:fix, format and tests, in src/ and then in every folder above it
yarn review

# 4.  What changed:  the branch, how far it is from main
epic worktree repos

# 5.  One commit, whichever folders it touches
git commit -am "README-development:  the loop first"

# 6.  main moved meanwhile?  Merge it in, regenerating the generated files
epic worktree merge-main

# 7.  In Claude Code, /isolate done:  it asks, then merges into main

That's every part of Spell, changed and checked as one, and nothing in the loop publishes anything: no npm link, no version bump. Every folder runs the others' SOURCE through one install, so the folders above your change are running it already, and yarn review checks them.

Written for: anyone changing Spell's code, its configs, its tool versions or its READMEs Checked: 2026-11-21, every script, version and file against that day's code The references beside it: the development README and the toolchain README
  • One repo, one install, one yarn.lock: the kit's src/, and four big folders beside it (parser/, ui/, epic/, app/).
  • Every folder answers to the same four checks, ts, lint, format, test, and review runs them all.
  • One dev dependency, vite-plus (command vp), pins vite, vitest, oxlint, oxfmt and oxlint's type-aware half together.
  • The lint and format settings are code, imported from spell/toolchain/lint, not a published config.
  • The READMEs are linted and their examples run: yarn readme:check, readme:test, readme:pictures.
  • Which command, skill or script does what is the commands page's job: a generated table of every one, among the guides.

Every folder answers to the same script names, so yarn test means the same thing in each. review is the one to run before you commit: it CHANGES files.

check what it does
ts the type check: the folder's programs and its tests', reading every folder below as source
lint oxlint, strict: a warning fails, and so does an unused disable comment; plus ruff, for Python
format oxfmt, and ruff's formatter for Python, over the folder's own files; it rewrites them
test Vitest, every project in the folder; then pytest for its Python
review ts, lint:fix, format, test, stopping at the first that fails; then "REVIEW PASSED"
  • At the root, each runs the kit's own (kit:ts ...) first, then each folder's, lowest first, and carries on past a failing one.
  • One folder: its own scripts, in its folder, cd ui && yarn test.
  • One test project: yarn vp test run --project server; one file: yarn vp test run Router.
  • yarn tsc, never npx tsc: yarn picks the install's TypeScript 7.
  • Done means three things: yarn review passed at the root, you read your own diff, and you reported the test count and how it moved.
  • The catch: vp fmt at the KIT's root reaches every folder with only the root's ignore list. Format the kit with yarn kit:format, a folder with its own yarn format.

Vite, Vitest, ESLint, Prettier and a type-aware lint plugin are usually five dependencies on five release schedules. Spell has one, vite-plus, and it pins a set known to work together.

    • vite-plus: 1.5.1
    • vite: npm:@voidzero-dev/vite-plus-core@1.5.1, Vite+'s own build
    • vitest and @vitest/*: 5.1.0
  • Bump them all together, to what vp toolchain lists; never one tool on its own.
  • The type checker isn't in the set: every folder names TypeScript 7, the native compiler.
  • Node 24, at least 24.11 (engines); yarn 4.18, through corepack.
  • The cost: Vite+ is the same engines, repackaged, so a dev server or one folder's tests run no faster. Its pins trail the standalone releases by a release or so.

ESLint shares rules through extends, a name that resolves to a published package. Here each folder's ONE vite.config.ts imports the settings like any other code, and spreads them in.

the parser folder's vite.config.ts, but for its docstring · 10 lines 
import { defineConfig } from "vite-plus"

import { fmtConfig, packageLint } from "spell/toolchain/lint"

/** Not linted or formatted by oxlint / oxfmt:  Python (ruff's). */
const NOT_OURS = ["src/py/core/**", "tests/py/core/**"]

export default defineConfig({
  fmt: { ...fmtConfig, ignorePatterns: [...fmtConfig.ignorePatterns, ...NOT_OURS] },
  lint: packageLint({ react: true, ignorePatterns: ["build", "dist", ".cache", "docs", ...NOT_OURS] })
})
  • spell/toolchain/lint is the toolchain's lint.ts: 120 columns, 2 spaces, no semicolons, double quotes, no trailing commas.
  • Markdown is left as written: the settings skip *.md.
  • Linting is type-aware, but never a second type check: yarn ts already runs tsc.
  • The house's own rules, beside it: the component rules (spell-ui/*), and the import rules (spell/no-parent-import, spell/no-upward-import).
  • Tests import from vite-plus/test, and configs from vite-plus; the lint rule vite-plus/prefer-vite-plus-imports holds them to it.
  • yarn oxfmt and yarn oxlint don't work: they're vp's, not dependencies of their own. yarn vitest does.

Every big folder has a front page, its README.md, and a README-<topic>.md beside it for each major folder or topic; the kit keeps its topic pages in README/. The kit's front page indexes all 44.

  • First for developers who know another framework, by contrast with what they know; second for coding agents. The rules for working on the code stay in the folder's AGENTS.md, which the page links.
  • In the readme voice: proof first (real code, real output), the model, the edges, then the next command.
  • A plain lead, then short sections of bullets; a table for three or more rows of one shape. Details fold into expands, and the page reads whole with every expand closed.
  • Setup is written for a Node novice: every command complete, from a named folder, with what it printed.
  • Pictures are Mermaid blocks, each with a one-line italic caption; yarn mermaid:pretty gives them the Spell look.
  • A planned feature gets a "🌱 Coming" stub: what it will do and where it stands, never a date.
  • "Spell" is capitalised in prose; "people", never "users"; no internal repo is named. A link into another folder is its GitHub address.
  • Every page ends with See also: at most five links, each with the reason you'd follow it.

Four scripts at the kit's root keep the pages true. Each takes page paths, from the kit's root.

run what it does
yarn readme:check follows every link to its file and heading, wants a caption under every picture, fails stale names; exits 1 on any finding
yarn readme:test runs every command a page shows with an Output fold, and fails one that prints something else
yarn readme:pictures draws every html example block headlessly, light and dark, into a picture under it; the check fails a stale one
yarn mermaid:pretty gives every Mermaid picture the Spell look, in place; safe to run again
  • Three of them are spell readme check, spell readme test and spell readme pictures too.
  • A tested example is an sh block, then a fold titled Output holding a text block. It runs in bash, from its page's repo root.
  • What it prints must match line by line, but for ...: alone on a line, any lines or none; inside a line, any text there.
  • A fold titled anything else, such as What it printed, is shown but never run: for installs, servers and anything slow.
  • Two folders write a table of their own: Spell UI's yarn readme:components, and the app's yarn examples:readme.
  • The editor's lint reads only the nearest config: a nested vite.config.ts inherits nothing from the root's, so it spreads packageLint() itself.
  • The format check skips Markdown: the README check is the only check a README gets.
  • The repo checks aren't spell commands yet: spell lint and spell format check and tidy .spell programs, not TypeScript.
  • The extensions are yarn projects of their own: the app's vscode/ and the epic folder's each need their own yarn install.
