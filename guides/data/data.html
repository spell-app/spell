Data

One line says where a program's things live. The rest of the program reads and changes them as if they were in memory: it waits, cancels, saves, heals and shares by itself.

Written for: someone writing a Spell program that keeps data, or working on the code under it Status: built; real Google Sheets, Airtable and AT Protocol accounts are still to be tried by hand
  • Where is one line: family cookbook is a web server at "...", then it lives in family cookbook on each type kept there.
    • Changing that one line moves the data, and nothing else in the program changes.
  • Reading waits by itself: a drawing that reads shows a loader, then the things; leaving it cancels the request.
    • <for> adds Try again, an empty message, pages and a title.
  • Changing is saving. There's no save step: each change is kept on the device, sent when its action ends, undone by undo, and healed when the server says no.
  • Several people settle: two people on one thing see it wobble, then agree.
    • Per field, the last change wins, with a notice for the one who lost; no CRDT.
  • The server's spelling is its own business: its "hair color" is text finds hair_color.
    • And "1,200" reads as a number.
  • Real servers, untouched. Seven public APIs come in through spell place ingest with no hand edits: PokéAPI for PokéSpell, and six more in the Public Servers example.
  • A copy on this device, when asked. keep a copy on this device makes a reload before the next check send no request at all: Star Wars' second load sends 0, its first 6.

  • at and from mean the same.
  • A server that can't say what changed is asked again: check it every 5 minutes.
    • Or check it once a day at 5am, which reads again when 5am comes round on the person's clock.
    • at 5am UTC goes by the server's clock instead.
  • A server that searches says so: it searches names with "search".
    • Then every character where its name includes the search asks it, with ?search=sky, not every page.
    • The program still checks what comes back; the ingest finds the parameter by trying one.
  • A key is named, never written: it is authenticated with the secret "COOKBOOK_KEY", kept on a server side. A key written into a program won't compile.
    • A server that doesn't want it as Authorization: Bearer says where: its secret goes in its "X-Api-Key" header, or its secret goes in the address as "api_key".
  • spell place ingest <address> --into App.api.spell looks at a real server and writes these lines, one server to a file.
    • Its description goes beside them, App.api.json5, which the project file names in development.apis.
    • spell place update App.api.spell looks again.
  • A server with an OpenAPI description is read from it whole: spell place ingest <address> --spec <its description>.
    • Every list, field, write and action route comes from its schemas, with no cap: NetBox's demo gives 143 lists.
    • Nothing is read from the server yet, so each type says this type is unverified. spell place verify App.api.spell reads each list and one thing of it by its id, and turns that into this type is verified or this type is failed.
    • When, where, its status and why stay in App.api.json5, each collection's state.
  • What a server lets be done to a type's things is a line on the thing: enabled operations are read, add, change.
    • No line means every operation; a line only narrows. read alone is read only.
    • An action route joins the list by its name: enabled operations are add, complete.
    • all operations are disabled turns the whole route off, reading too.
    • The same line one step in under a collection's live at line is the switch for all of them; a thing's own line can only narrow it.
    • What's left out still compiles, and says so when it runs: "Jobs can't be deleted here."
  • A key that's a short-lived token made from a secret: it is authenticated with a token from "https://auth.example.com/api-keys/{key id}/token", made with the secret "ACME_API_KEY". Spell makes it, keeps it, and makes another before it runs out.
  • its data is private, located in "~/.spell/places/acme": no real value goes in the description, and the rows read go in that folder. spell place ingest --no-examples writes it.
  • One place, several deployments (dev, staging, production): the project's file lists them under places, each its own address, key, and read only or not. --deployment or SPELL_DEPLOYMENT picks one for spell place verify, which never writes to a read only one.

  • Lists side by side (one list of hours, one per measure) read as one thing per hour.
  • A map keyed by a code ("EUR": { ... }) reads as a list of things, each with its code: its "currencies" is a list of currencies.
## Family Cookbook: your recipes, saved in the cloud family cookbook is saved in the cloud a "recipe" is a thing it lives in family cookbook its "title" is text its "servings" is a number its "notes" is text
  • That line is a folder of each person's own on Spell's server: their space's __data/family-cookbook.
    • Signed out, every change stays in this browser, and the sign-in bar says so.
    • Signed in, the changes go up within seconds, and every device they sign in on sees them.
    • In Spanish: recetario familiar se guarda en la nube.
  • A Firebase or Supabase app gets the same from an SDK, a console and a config file. Here it's the sentence: the rest of the program reads and saves the way it did on this device.

A data folder by its address

  • family cookbook is a data folder at "owen@spell/recipes" keeps its rows in that space's folder.
  • "recipes" alone is the program's own folder, shared by everyone who runs it.
  • personal "recipes" is one per person, in their own space (Spanish: carpeta de datos personal en "recetas").
  • A data folder is asked what changed at most every 5 seconds: a faster check it every is raised to that, with a warning at the line.
  • task sheet is a sheet at "tasks.csv" and a json file at "recipes.json" work the same way: a file's name alone is a file in the program's own folder, which takes writes.

Signing in

  • People sign in by email: a link and a 6-digit code. The link works on any device, and the device that asked signs in too.
  • It's invite only: an invite makes the person's Spell account, ana@spell. Once signed in, they can link a Bluesky account, and sign in with it after that.

Sharing a space with its members

  • A space's own folder (@family/cookbook) is written by its members. A program's own data is each row's owner's only.
  • Every record in a members' folder is the space's, with by naming who saved it: Ana and Bo editing one recipe keep one record.
  • Each member has one of three roles:
    • viewer: reads, and posts and comments where the space allows it
    • editor: also adds rows and files, and changes any of them; removes only their own
    • manager: also makes new pages and apps, publishes, removes anything, and adds people
  • Changing a program's own pages is a right of its own, design: managers have it, and an org gives it to anyone else.
  • A member may always leave; the last manager can't.
  • Anyone else is refused, in English and Spanish: "Your role can't write here: you aren't a member of @family". A refusal names the role it takes: "it takes an editor".
  • Limits: 1 MB a thing, 100 MB a space. A save over either is refused, and stays on the page.

Not yet: a public address. Spell's cloud server runs on this machine, and its mail lands in a catcher here (spell space cloud mail reads it); going live waits on a public host and a real mail service. Orgs, their roles and spaces, and running the server: the spaces README.

A server's actions

A server's own action, to complete a job is at "/api/jobs/{id}/complete", is an action of the job like any other, and steps can run around it, from any file.

  • Called on a job held, complete the job, or by its id, complete job 7151: read first unless it's held. None there, and its failure steps hear "not found".
  • Its other blanks are sent by name and fill its address's braces: to move a job to (queue as text) is at "/api/jobs/{id}/move/{queue}".
  • before completing a job runs first, and cancel there sends nothing. while completing a job sets what shows while the server works, put back when it answers. after completing a job runs once it has.
  • if completing a job fails (or when ... fails) hears what went wrong: if the error is "not found", then nevermind to drop it, or pass the error to send it on. Its last if, with no otherwise, passes on what no branch caught.
  • The error's names: "not found", "not authorized" (not signed in), "not permitted" (signed in, not allowed), "out of date", "server not found", "limit", "offline", and "anything", what if that fails means.
  • The app's own, when any server call fails, runs last, for what the others passed on; then Spell's notice, only for what nobody caught. otherwise do nothing there keeps the notice away.
  • The order, from the file each is in: before and while steps from a page's file first, then the app's, then the .api.spell file's; after and failure steps the other way round. A page's before and while steps only run while it's shown; its after steps even once it's left.
  • A second to complete a job wraps the server's: call netbox (or, in the API file, call the server) runs it where it says. One that never calls it is warned of.
  • Spanish: antes de completar un trabajo, mientras se completa un trabajo, si falla al completar un trabajo, el error es "no encontrado", no importa, pasar el error, cuando falla cualquier llamada al servidor, llamar al servidor.
  • The person using the program: they, them.
    • Or their name, the person.
    • everyone here is who's in the room now.
  • when someone else changes it runs for another person's change only.
  • A room's referee gives every change one order: two people settle in about half a second.
  • A field finds the server's spelling by its words: its "hair color" is text.
    • It reads hair_color or hairColor.
    • Even Hair Color.
    • It saves under the spelling it read.
  • Only a name that really differs says so: its "title" is text, stored as "dish_name".
  • A number read as text is a number: "172", "1,200".
    • And "1,5", "1.200,5".
    • it writes numbers like "1.200,5" settles an unclear one.
  • is a number or "unknown": the server's word for none, read quietly, and written back when you save nothing.
  • A number or date the server didn't send is nothing, not 0.
  • A date shows the way its text says: {its created as a date and time} is Nov 7, 2026, 9:14 AM (Spanish como fecha y hora).
