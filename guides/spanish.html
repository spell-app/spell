Spell in Spanish

"es una figura" si su rango es jota, dama o rey is a line of Spell, from a Spanish card. It compiles to a getter, get esUnaFigura(), and a test that uses it prints ✅ Como se esperaba when it passes.

Spanish is the second language Spell reads, and in Spanish Spell is called Encanto. It isn't a translation layer over English, and it isn't a second parser: the same rule classes are registered twice, once with English words and once with Spanish ones, and each file's name says which set it's written in.

Written for: someone writing Spell in Spanish, or turning an English project into a Spanish one Status: built; Solitario, Solitaire in Spanish, is an example of its own, and spell translate writes any English project in Spanish The same, for programmers, with every command's output: the Spanish README
  • A file's name says its language: Carta.es.spell is Spanish, Card.spell (or Card.en.spell) English. One project may mix them.
  • A Spanish file says each line in Spanish, una "carta" es una vista beside English a "card" is a view, and the words keep their accents: su "palo", para voltearla.
  • It parses with Spanish words, plurals and articles, and compiles to the author's names, accents kept.
  • Every language is a LANGUAGE PACK: its rule words, its word tables, its inflector (singular and plural) and its messages. English is the first pack, Spanish the second.
  • A wrong article is a warning, in both languages:
    • el carta asks ¿Querías decir "la carta"?
    • a apple asks Did you mean "an apple"?
  • Spell UI's components have Spanish names on a Spanish page: <es-boton>.
  • The editor, VS Code and the parser's messages speak each file's language, and a test's lines the program's; the editor's own buttons and panels speak the page's.
  • spell translate writes an English project again in Spanish: its names first, then each line by its own rule, then Claude fixes what fails.
  • Name its files .es.spell.
  • The example @spell/examples/Solitario, Solitaire in Spanish file for file, is a whole project to copy from.

Solitario is the Solitaire example written again in Spanish, file for file: its own card, deck and piles (Carta, Mazo, Pila), the game, and their tests. Its project file is an ordinary one: each file's name says it's Spanish.

A Spanish file reads the way an English one does, word order and all.

What Spanish needed that English didn't:

  • Articles with gender: un / una, el / la / los / las, and two contractions, del and al.
  • Spanish plurals: accents move (corazón / corazones), and some words don't change (lunes).
  • Two verbs for "is": es and está both mean "is" to the parser.
  • A dropped subject: tiene un mazo needs no "it"; su / sus stand for "its".
  • A property read inside an action: barajar la reserva for barajar su reserva, and poner la puntuación a 1 writes it.
  • The decimal comma: 1,5 is a number, 1, 5 a list of two.
  • Accents in names: año is one word, not three tokens, everywhere a word is matched.

One project may mix languages. A Spanish file names an English type by its own words, and calls its English methods: un equipo es una lista de players, then reset el p.

The catch: a plural English name in a Spanish file is made singular by Spanish's rules. players finds Player, but una lista de cards looks for a type named Cards: to Spanish, one syllable ending in -s is already singular, as mes is.

Names are the author's, accents and all: esUnaFigura, dirección. The runtime's own calls (core.includes) stay English, because nobody reads them.

spell compile @spell/examples/Solitario --stdout, from Carta.es.spell · 12 lines 
  get color() {
    if (this.palo === "diamantes" || this.palo === "corazones") return "rojo"
    return "negro"
  }

  get esUnaFigura() {
    return core.includes(["jota", "dama", "rey"], this.rango)
  }

  get esUnaCartaNumérica() {
    return !this.esUnaFigura
  }
  • esUnaCartaNumérica is a legal name in JavaScript, TypeScript and Python 3, so Spell keeps the accent. Two ways of typing é are one name.
  • --target py writes es_una_figura, the same getter as a Python property.
  • Each language in a project gets its own words file, which maps each compiled name back to the words that declared it: Solitario.es.js beside an English project's .en.js.

A parser generator gives each language its own grammar file. Spell keeps ONE set of rule classes, the code that says what a rule compiles to, and gives each language its own words for them.

  • Each rule's class is a file of its own, with nothing about words.
  • Beside them, <module>.en.ts registers every rule of the module with its English syntax and tests, and <module>.es.ts the same rules, in the same order, with Spanish's.
  • A third language is a third file per module.
a rule module's folder · 4 lines 
parser/src/spell/rules/<module>/
  <Rule>.ts             the rule's class:  what it compiles to, in no language's words
  <module>.en.ts        every rule of the module, with its English syntax and tests
  <module>.es.ts        the same rules, in the same order, with Spanish's
  • The small words are WORD RULES each language registers: the articles, "is" or "is not", "it" ... some word rules, English and Spanish · illustrative · 3 lines 
    definite_article      the            el | la | los | las
indefinite_article    a | an         un | una | unos | unas
is_or_is_not          is | is not    es | está | no es | no está
  • A rule reads what its word rule matched (negated or not, which article), never the word itself.
  • A guard test fails if an English word comes back into rule code.

SP.Language is one language's pack, in parser/src/spell/languages, a folder per language:

  • its parser, with every rule registered in its words
  • its inflector: English's wraps the npm pluralize; Spanish's is ported from Python-Inflector's rules, and works both ways
  • its word tables: the identifier blacklist, booleans, number words, ordinals, the built-in types' words
  • its article agreement, and the messages a person reads
  • its glossary of the words chosen, so every module says poner, not fijar

Each file's scope picks its pack from the file's language, so its colours, completions and warnings follow. A Spanish program never loads English's inflector.

A new English rule must never leave a language behind without anyone noticing.

spell translate check es · 1 line 
Spanish (es):  complete, 21 modules
  • check compares each pack with English, module by module: a rule missing, out of order, or with no syntax or tests; and the word tables. It exits 1 on anything missing, and runs in the parser's tests too.
  • spell translate fix es writes a stub for each missing registration. With --ai, Claude drafts each one, marked for review.
  • A difference on purpose is marked in the pack's file, so the check passes: // packs: ok -- why.
  • A type's gender is read off its declaration: una "carta" es una cosa makes it feminine.
  • Spanish warns on gender and number: el carta, un cartas. English uses the same check for a apple and an card.
  • It's a warning, never an error: the line still compiles. A strict parser would need gender while it matches, and it doesn't have it.
  • spell compile and spell run print it: Prueba.es.spell:3:1 warning: ¿Querías decir "la carta"?.

On a Spanish page, every Spell UI component has a Spanish tag, Spanish attributes and Spanish texts. Solitario's toolbar is one:

<segmento invertido unir-a="arriba" color="">
	<barra-herramientas class="GameBar" aria-label="Juego" apariencia="pildoras" invertido tamano="pequeño" encogible>
		<texto slot="titulo" tamano="grande" extranegrita>Solitario</texto>
		<acción "jugar solo"/>
		<acción "hacer trampa"/>
		<acción "reiniciar el juego"/>
		<divisor/>
		<acción "deshacer" solo-icono/>
		<acción "rehacer" solo-icono/>
		<texto slot="derecha">Puntos: <número "puntuación"/></>
	</barra-herramientas>
</segmento>
  • In Spell, a bare name is Spell UI's tag: <texto> for <es-texto>. A Spanish view gets its tag from its Spanish names: <solitario-carta>.
  • On a plain page, its language is its <ui-root lang="es">, else the document's lang. Every component then loads on demand as es-*, its texts in Spanish.
  • Tag and attribute names are ASCII: es-boton, tamano. Values keep their accents, and are found without them too: pequeno finds pequeño.
  • A Spanish tag's properties are Spanish too: desplegable.abierto.
  • Only a Spanish page loads the Spanish.
  • Each component's Spanish sits beside its English, UIButton.es.ts beside UIButton.en.ts. How the names work: Spell UI's runtime README.
  • A keyword typed without its accent gets it back as you type a space or Enter: el numero de becomes el número de.
    • Both VS Code and the editor do it, so a Spanish file types on an English keyboard.
    • It never touches a word that's right both ways (si, sí), or a name a person chose.
  • VS Code and the editor colour Spanish keywords; their keyword lists are written from the packs, English and Spanish in one grammar.
  • si no: and de lo contrario go back out a level, as otherwise does.
  • In a Spanish file, completion offers Spanish keywords (si, para, devolver), and the Type Explorer's built-in types are Spanish's.
  • An accented word is one word to double-click.
  • The editor speaks the PAGE's language: the document's lang, else the browser's. "Guardar" where an English browser gets "Save".
  • The language server's labels (hover, completion, the Define fix, the Type Explorer) speak the language of the FILE they're about, in any editor: a Spanish program's hover says declarado en.

spell translate <project> --to es writes an English project again in Spanish, as a project of its own beside it. Solitaire came out linted clean and passing its six tests, with no person in the loop, in under a minute.

  1. Names: every name the project chose (types, properties, values, methods, texts, comments), each noun with its gender.
    • First from the Spanish glossary, shared by every project, so one English word is one Spanish word in every program.
    • The rest by Claude: the types first, then the other names in a few calls at once.
    • They land in the project's dictionary, <Project>.es.names.json5, for a person to review.
  2. Lines: each line read in English, then written again by the same rule in its Spanish words, articles agreeing. No model writes these.
  3. Fix-ups: the translation is linted, its tests run, and each statement compiled beside its English one. A line that fails, couldn't be written, or compiles to a different program goes back to Claude, in context, a few rounds at most.
  • Every translation comes back in plain Spell: Card.spell gives Carta.es.spell. A page file is left out: its body is prose and markup.
  • A line it can't write keeps its English, marked // TODO: translate, and the command exits 1.
  • <ui-*> tags, their attributes and values become Spell UI's Spanish ones, and a style sheet's selectors with them. A project it imports keeps its own words.
  • --update re-translates only the English lines changed since the last run: hand edits to the Spanish stay.
