Solid 2 in Spell

In Spell, set the score to 5 then print the score must print 5. In Solid 2, a write isn't visible until the next flush, even on the very next line. This page is what Spell needs to know about Solid 2 that the Solid docs don't tell you, and how Spell cells close that gap.

Written for: anyone writing Solid code in Spell (the editor, compiled Spell's drawing, Spell UI's components), or reasoning about Spell's reactivity Checked: 2026-11-26, on Solid 2.0.4 (2.0 final), every experiment beside this page re-run that day, on rc.21 and 2.0.4, with the same results The rules beside it: the Solid 2 rules, which every agent reads in full before Solid work, and which win where the two differ
  • Everything draws with Solid 2: the editor, <spell-viewer>, Spell UI's elements, and compiled Spell, in JavaScript and TypeScript alike.
  • Every package is pinned to Solid 2.0 final, 2.0.4 (@solidjs/h and the compiler 2.0.3), one copy at the kit's root: one Solid per page is not optional.
  • Spell state is NOT Solid signals. It's Spell cells: a plain record read and written at once, which Solid observes through one bridge. So a write reads back on the next line.
  • The traps are real: a write in a memo throws in dev, an uncaught error halts every update on the page, a direct store write is silently ignored.
  • Solid's own docs for agents ship inside solid-js (its skills/ folder, diagnostics.json): trust them first, then this page.

Solid 2 builds one idea: the reactive graph always knows. Here it is compressed, with what each part means for Spell.

A component is a setup function that runs a single time.

  • No re-render and no diff
  • Each dynamic JSX expression compiles to its own tiny tracking scope
  • Props arrive as lazy getters, so "passing isn't reading"
  • When a signal changes, only expressions that read it re-run and patch their text node or attribute
  • Compiled Spell hands Solid a function for every value that can change: h("span", { class: "suit" }, () => this.shortSuit).
  • Solid calls it, and again when what it read changes: nothing redraws a whole board.
  • Without a JSX compiler, as in @solidjs/h hyperscript, nothing else makes an expression reactive.
  • Each drawn thing sits in its own error boundary, so a draw() that throws shows a small stand-in and the rest keeps drawing.

Solid 2 batches every write.

  • A write is staged and committed with all its neighbours on the next microtask, or when you call flush()
  • Until then every read returns the last committed value, even a read on the very next line
  • That's the price of the headline guarantee: "at no point does the UI disagree with itself"
  • There is no batch(), because everything is a batch

A memo may return a Promise.

  • Everything downstream just waits
  • <Loading> covers only the first load
  • Once a value has shown, a new write that feeds async work is held:
    • old content stays on screen until the new answer lands
    • every other write in the same batch is held with it
  • That's what replaced transitions
  • isPending(x) asks "is something on the way?"; latest(x) asks "what is it?"

action(function* () { ...; yield api.save(); refresh(src) }) holds a transaction open across awaits.

  • Optimistic writes (createOptimistic, createOptimisticStore) are a layer over the confirmed value
  • The layer is dropped when the action settles, pass or fail, so there's no rollback code
  • Since 2.0.4 a guess never becomes the real value: it always goes back when its action settles, and an optimistic write outside an action does nothing (Spell writes none today)
  • Errors are another status of part of the graph: <Errored> heals by itself when the data underneath recovers
  • Spell is imperative: set the score to 5 then print the score must print 5
  • A worked-out property must be current on the very next line
  • Solid 2's staged commit is exactly what breaks that
  • So Spell state cannot be Solid signals as its source of truth
  • Spell state is a synchronous source that the graph observes: section 3

None of this is spelled out in the docs. Each row is a script beside this page (Experiments), re-run on 2.0.4: every one read the same as on rc.21.

  • An unowned, eager memo recomputes on every flush that touches its inputs, forever, even with no readers.
  • A lazy memo read from untracked code recomputes on every read, and memoizes nothing.
  • So nothing Solid provides gives a fresh read: latest doesn't see synchronous writes, lazy memos read committed values, there's no mutable store, and flush() per write is entangled with async.

Spell's own small reactive engine, spell/util/reactive, under every reactive class: compiled Spell's Thing and List, the editor, Spell's project objects.

  • The record is the truth: each object's own Map. Cells hold no value; they only know who read what.
  • Derived values pull: Derived, derive() and @derived re-check their sources, and notify only if their value really changed.
  • Readers are Reactions: one per Solid computation, one per observe(). A reader never re-runs for a change its own run made.
  • One cells context per page, on globalThis (Symbol.for("spell:cells")): the app's spell/util and every spell-runtime.js copy share it. CONTEXT_VERSION guards its shape.
  • Values aren't made reactive: no proxies, so === holds everywhere.
    • The catch: change a list or object a prop holds IN PLACE, and nobody hears. Set the prop to a new one instead; Spell's List copies on write.
  • The DOM lags Spell by one microtask. Tests and imperative code call core.flush() (flushCells()): pending derived checks, then the host's Solid flush(). Never Solid's own directly.
  • The engine's files: src/util/reactive/, and the util folder's AGENTS.md, "The reactive engine".
  • keys() lists a thing's own properties in the order they were first set.
    • An overwrite keeps the position; a delete takes the key out; setting it again appends it.
  • The record is a Map because an object hoists integer-like keys: b, 10, a, 2 comes back as ["2", "10", "b", "a"].
  • keys() tracks a keys cell of its own, changed only when the key set changes: a property list redraws when a property appears or goes, not on every value change.
  • @props are keys, and toJSON() lists them; @state is internal, never listed.
  • Each class has a schema, schemaOf(Class): a type per property.
    • Compiled Spell declares them, static { this.declareProp("rank", { ... }) }.
    • Hand-written classes declare them with @prop({ type, default }).
  • An undeclared property's type is observed per class, widened on a mismatch, with a dev warning.
  • Thing and List check a declared type on the program's console when a value changes; the value is still stored.

Hand-written classes use standard (TC39) decorators, from decorators.ts; compiled Spell writes the same runtime shape without them.

  • @prop(info) accessor x!: T: a reactive prop, listed by keys(), declared in the class's schema. NEVER an initializer: say { default: 1 }, or { init: () => [] } for an object made once per instance.
  • @state accessor x = v: internal state, never listed; the initializer is its start.
  • @derived get y(): memoized, its readers re-run only when its value REALLY changes. Only for pure, worth-it getters: memoizing a cheap one is about 2x slower.
  • @state({ equals }) and @derived({ equals }): an equal value is no change.
  • @thing, Spell's own (spell/util/spell): runs create() exactly once, after the most-derived class's field initializers.
  • Spell UI's components have their own with the same names and options: Custom Elements.
  • A decorator must start its line: the toolchain's decorator pre-pass looks for it there.

spell/util and compiled Spell's core never import Solid. So the HOST wires cells to Solid, once.

import { enableExternalSource, flush } from "solid-js" import { bridgeSolid } from "spell/util" bridgeSolid({ enableExternalSource, flush })
  • bridgeSolid() makes EVERY Solid computation (a JSX expression, a memo, an effect's compute) a cells reader, so a plain {editor.notice} in JSX is reactive.
    • The editor app calls it in cellsBridge.ts, imported before anything renders.
  • ONCE per Solid, however many hosts call it: Solid pipes every enableExternalSource() into the last, so a second would wrap every computation twice. The cells context remembers it.
  • Solid re-runs readers on ITS schedule: never in the middle of a program's own writes, and ten writes re-run a reader once.
  • tracked(read), in the app's tracked.ts: one Solid memo over a read of Spell state, however many places read it. Its value is Solid's, so it's staged; a plain editor.x read never is.
  • observe(fn) re-runs a plain function at once as what it read changes.
  • One Solid per page: the app's bundles share spell-solid.js, which holds Solid, Spell UI's element core and the h() compiled Spell draws with; the runtime takes Solid from the page, never a copy of its own. README-app, "How the bundles share one Solid".
  • enableExternalSource is global: registering it wraps every Solid computation on the page, Spell UI's included.
  • Check timing: derived-only readers are re-checked in a microtask, which may come after Solid's own flush. That costs a second small pass, never a wrong value.
  • Equality is ===: a new array with the same contents counts as a change. It errs toward updating.
  • Cycles: a derived value that reads itself overflows the stack; there's no Spell-level error for it yet.
  • No async in cells: Spell values are synchronous. A fetched value enters through a Solid async memo at the UI edge, never a cell, which keeps Spell immune to holds.
  • Memory: cells and derived values are made lazily, referenced only from their object and their readers; bridge nodes unlink on dispose.
  • An effect's apply function returns its cleanup. createRenderEffect(() => x(), v => list.push(v)) returns a number, which Solid then calls; the dev build throws PRIMITIVE_IN_EFFECT_CALLBACK. Always write v => { ... }.
  • One uncaught error halts every later update, page-wide (REACTIVITY_HALTED). A buggy Spell program must never take down the editor around it:
    • each drawn thing sits in its own <Errored> boundary
    • each Spell UI element has its own boundary too
    • resetErrorHalt() exists for recovery
  • Owned-scope writes throw in dev, even in a createRoot body. Spell cells never write Solid state, so Spell is unaffected; app code still follows the rule.
  • Memo lifetimes: a non-lazy memo lives until its owner dies. In app code, make memos inside components, never at module scope.
  • Holds are narrower than the docs say: a write feeding async work is held only when a render effect reads the async value with no <Loading> to catch it. Later batches go through.
  • No mutable store: a direct write to a Solid store (s.a = 2) is ignored; dev warns STORE_WRITE_OUTSIDE_SETTER, production says nothing. Hence the editor's store is on Spell cells.
  • Stores wrap class instances: createStore({ card }) hands back a proxy, and === against the raw thing fails. Never put a Spell thing in a Solid store.
  • The 1.x forms are compile errors since rc.17: on:, attr:, bool:, use:, classList.
  • On a tag with a dash, Solid sets a plain prop with setAttribute(). Spell's own elements take a function or object as itself; anyone else's turns it into text, so rich data there is prop:options={...}.
  • Only on and an uppercase letter is an event, its name lowercased: onUIChange listens for uichange, not ui-change.
    • On Spell's elements, write the event's own name: on-ui-change={f}.
    • Any other element's dashed event: a ref that adds the listener.
  • Portal defaults to document.body: inside a shadow root, pass mount, or content and styles escape.
  • React habits that silently break: destructuring props reads them once; class, not className; onChange is the native change event, so use onInput; refs are callbacks; the context is its own provider.
  • The arity trap: hyperscript turns a zero-argument function prop on a component into a getter. h(Comp, { onPick: () => go() }) passes the result of go(); a handler takes an argument (e => go()). Compiled Spell's handlers take (event).
  • @solidjs/h imports @solidjs/web by bare name, so compiled Spell never imports it directly: it imports only @spell/core, which takes Solid from the page.
  • Two Solids on one page fail SILENTLY: each copy has its own graph, so an element built by one never hears a change made through the other. A second copy's UIComponent.define() finds each tag defined and keeps the first copy's class.
  • Under Node, @solidjs/web resolves to its server build, with no DOM render: component tests run in a real browser (Vitest's browser mode).
  • After any event, flush before asserting.
  • Every package is pinned exactly, in the kit's root resolutions, and upgraded together: solid-js, @solidjs/web and @solidjs/signals at 2.0.4, @solidjs/h, the compiler and the Babel plugin at 2.0.3.
  • On a Solid upgrade, run the experiments on the old and the new Solid and compare: SOLID_NODE_MODULES=<dir> picks the one an experiment loads.
  • What changed from rc.13 to 2.0, and bit us, is in the Solid 2 rules, marked with the release.

Ways Spell UI could use what Solid 2 gives. Not built, but the first.

  • Read-after-write on element properties: built. DOMElement keeps one plain record of attribute values, up to date at once: el.value = 3; el.value reads 3.
  • Async options with no loading flags: <ui-dropdown> could take a function that returns a Promise, made an async memo inside; isPending() would drive its loading look.
  • createProjection for selection: only the two rows whose selection changed would update.
  • action and createOptimistic for form controls: a checkbox bound to a server write shows its new state at once, and falls back on failure.
  • unobserved callbacks: start a ResizeObserver or IntersectionObserver only while something reads the value it feeds.
  • <Repeat> for table virtualization: it renders a window by index, with no diffing.
  • Context across elements: with one Solid per page, an app's context (theme, locale) can reach every element's render.
  • Errors that heal: an element's fallback could draw again when its inputs change, instead of staying in :state(errored) until reload.
  • Refuse a cross-Solid swap loudly: stamp each class with its Solid, and on a mismatch log one clear "two Solids on this page" error.

What's new or different in Solid 2, from Solid 1 and from React habits, a line each. Solid's own cheatsheet, as a skill, is in solid-js's skills/solid-2.0-cheatsheet/.

  • The reactive core is @solidjs/signals; solid-js re-exports it and holds stores too. solid-js/web is @solidjs/web; solid-js/h is @solidjs/h.
  • JSX: "jsx": "preserve", "jsxImportSource": "@solidjs/web". Custom elements are declared on "@solidjs/web/types/jsx.js".
  • Vite: @solidjs/vite-plugin, after the decorator pre-pass, so Solid's compiler sees decorator-free code.

Code Means, and the fix
REACTIVE_WRITE_IN_OWNED_SCOPE a write in a component, memo, effect compute or root body: move it to a handler or onSettled
STRICT_READ_UNTRACKED a reactive read in a component body: move the read to where the value is used (JSX, a memo, an effect's compute, the handler, an accessor handed to a hook); don't destructure props. Never untrack() it to quiet the warning (Solid's own advice since 2.0.4): the value still goes stale
REACTIVITY_HALTED an uncaught error stopped the scheduler: <Errored>, an effect's error
NO_OWNER_EFFECT an effect outside any owner: make it in a component or createRoot
UNSTABLE_LIST_IDENTITY .map() in JSX, or fresh objects per update: <For>, keyed by id
