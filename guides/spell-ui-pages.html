Spell UI's Docs Site

 <ui-section id="examples-types-button" label="Button" sticky collapsible dividing> <ui-example description="A standard button."> <ui-button>Follow</ui-button> </ui-example> </ui-section>

That's the first example on the Button page, and all of its source: in the browser it's a live <ui-button> with a code button that shows these same lines. The site is 121 plain HTML pages with 2,159 live examples like it, laid out as fomantic-ui.com's are, and nothing is built between saving a page and reading it.

Written for: anyone adding a component's page, or changing how the site draws Checked: 2026-11-21, every count, path and script against that day's code The reference beside it: README-site, every script and file in full
  • 121 pages (counted 2026-11-21):
    • a page per component family, 96 of them, each named for its main tag (ui-button.html)
    • a page of its own for 15 sub-tags: ui-radio, ui-textarea and the content parts
    • ten more: the home page, getting started, the class grammar, theming, utilities, icons, the palette, the theme bench, the component index and the kitchen sink
  • 2,159 live examples, each showing its own markup: an example is written once.
  • Everything visible is a ui-* element. The site's CSS is layout glue only; a rule there that changes a look is a gap.
  • A gap gets fixed in the element, never patched in the page. A page that can only use the library shows where the library falls short.
  • If you've written Storybook stories: a story is a function, built into an app of its own. Here an example is markup in a plain page, which the page server sends exactly as it is on disk.
spell server start all

Then open the docs site's row, /components/ui/ on the page server. Three things make the site:

What Where Made by
the pages ui/docs/, one flat folder, tracked with the branch hand
the data ui/docs/__data/, generated and committed yarn site:data
the bundle ui/site/_assets/, from ui/site/_src/; never committed yarn site:bundle, or the page server, when stale
  • The page server lays the bundle over the pages at /components/ui/_assets/, because Spell UI's part of its settings names the set.
  • An open page reloads when the page, its layout, its data or the bundle changes.
  • Every component set's pages load this one bundle: Epic UI's at /components/epics/, App UI's at /components/app/.
  • __parts/layout.html is every page's chrome, written once: the top bar, the side column, the <ui-root>. __parts/footer.html its footer.
  • ui/docs/examples/ holds the files the examples load; ui/docs/images/, Fomantic's docs images, at fomantic-ui.com's paths.
  • Three catches:
    • a page opened from disk shows bare markup: there's no _assets/ beside it
    • spell server url <file> doesn't know the docs site yet: use /components/ui/<page>
    • the main checkout's server never builds a worktree's bundle: after a change to its sources there, run spell bundle in the worktree, naming ui-site
<head> <title>Button | Spell UI</title> <meta name="description" content="A button indicates a possible user action." /> <link rel="stylesheet" href="_assets/site.css" /> <script type="module" src="_assets/site.js"></script> <script defer src="/_epic/assets/spell-comments.js"></script> </head> <body class="ui-typography"> <main id="main" class="site-main" data-toc-header="Button"> <!-- the masthead, then <ui-tabs id="site-tabs"> and its four panes --> </main> </body>
  • No top bar, no nav, no <ui-root>: the bundle puts the page's main inside the layout.
  • The model page is ui-button.html: open it beside yours, and copy its patterns.
  • Links are written as from the page's served address: _assets/ is beside it, ../epics/epic-item.html another set's page.
  • Hidden until it's all there: the site's CSS hides the bare main, 4 seconds at most, while the bundle fetches the layout, wraps the page in it, puts in the viewer's theme, then defines <ui-root display="when-ready">, which shows the page once every element is ready.
  • The examples' markup is kept FIRST, before anything upgrades, so the code an example shows is what you wrote.
  • After the first page, a click doesn't load a page: the site's router fetches the next one, swaps only the main, and pushes its real URL. Back, forward, deep links and reloads work as with plain pages.
  • The catch: inline scripts in main run again on every visit, and <head> styles DON'T follow a swap. Put a page's styles in its main.
  • The layout's root is <ui-root class="site" stack-with="page">, so an example stacks by the SCREEN's width, not the docs column's.
  • Examples: a section per topic, an example a section of its own inside it.
  • Usage: what to write, the events with their detail, keyboard and accessibility.
  • API: done already. <ui-docs-api family="ui-button"> draws every table from the site's data, a section per kind (Attributes, Events ...), a Tags section first for a family of 2+ tags.
  • Theming: <ui-docs-tokens family="ui-button" playground>, the family's tokens live on its main example.
  • An "On this page" rail beside them, at 1200px and wider; a left nav lists every component, A-Z or by topic.
  • Every section's title sticks below the tabs' bar; sections fold, remembered per page, and a link (#examples-types-emphasis) opens the tab and unfolds what hides it.
  • People comment on these pages as on every guide: the bullhorns, threads and Send, from /_epic/assets/spell-comments.js in each page's head.
  • The layout loads the epics pack, whose elements draw the threads and the pane.
  • A comment waits beside its page in <page>.inbox.json5, git-ignored, until Send hands it on.
  • The cost: a page loads 555 kB of script and CSS before its first family, 155 kB gzipped; 305 kB, 79 kB gzipped, without what the pack shares.

The site's own widgets, written exactly like a component family, in ui/src/docs-components/:

  • <ui-docs-api>: a family's tables, from its vocabularies
  • <ui-docs-tokens>: its tokens, and the playground
  • <ui-docs-inspector>: an element's attributes, properties and states, live
  • <ui-docs-nav>: the side column; <ui-docs-search>: the search
  • <ui-docs-index>, <ui-docs-palette>, <ui-docs-theme-bench>: a site's index page, the editor's palette and the theme bench
  • <ui-example>, <ui-toc> and <ui-theme-menu> began here, and are real components now.
  • Not components: no library entry, and <ui-root> loads them only where the page's bundle asked for them (the site's does).
  • The elements read __data/components.json5, never the vocabularies: every tag, family, token and topic.
  • icons.json5: the icon browser's search terms; search.json5: every page's sections.
  • Beside them, what editors read: custom-elements.json, html-custom-data.json, css-custom-data.json.
  • pages.json5 is kept by hand: each family's title, summary, status, and its sub-tags with a page of their own. Fix a summary there, then yarn site:data.
  • A new doc-only element is a family folder like any other; the barrel's header says how to add one.
  • A widget other pages need moves into the components folder instead, its old tag renamed.
 cd ui yarn site:new ui-card yarn site:new getting-started --title "Getting started" --summary "One line."
  • A tag writes its page, docs/<main tag>.html, from the template when it isn't there yet, and its four pages in the Spell UI site, as Spell.
  • A sub-tag its family lists under pages gets a page of its own, one tag's API.
  • Anything else is a guide page, one column, no tabs.
  • It refuses to overwrite a page; --force does, and loses what you wrote.
 <ui-header level="2" dividing>Types</ui-header> <ui-example heading="Button" description="A standard button."> <ui-button>Follow</ui-button> </ui-example>
  • Write it flat, a level 2 header per topic; yarn site:sections nests it into sections and writes their ids, and running it twice changes nothing.
  • Fomantic's page, section by section and in its order; our extras after.
  • The only attributes are the family's vocabulary's; the markup IS the code shown, with no style=.
  • A Fomantic feature left out on purpose gets one line in its place: <ui-message size="small" class="site-not-ported">.
  • What an element can't render yet is a gap: a comment before its example's section, naming its issue.
  • An example whose markup changes as it runs holds it in a <template> child.
Script, from ui/ What it writes
yarn site:data the site's data, the editors' manifests and the JSX types
yarn site:index the component index's cards
yarn site:kitchen the kitchen sink, and each Theming playground
yarn site:bundle the bundle, site/_assets/
yarn site:build the four above, in turn
  • Run yarn site:build after changing a vocabulary, a family's sheet, an example, or anything the site shows.
  • --check writes nothing, and exits 1 if a file would change.
  • A stale bundle, by hand: spell bundle check ui-site, then spell bundle, naming ui-site.
  • yarn site:dev: the bundle, then a watch build that rebuilds it on every source edit, while the page server serves the site and the open pages reload.
  • It doesn't watch the data, the index or the kitchen sink: rerun yarn site:build for those.
  • Just the elements, no server: yarn dev opens the demo, every example beside its class grammar.
  • yarn site:check <page...> (or --all) loads the Spell UI site's pages, as this checkout's editor runs them, in headless Chromium.
  • It fails on console errors and failed requests, undefined elements, an empty contents list, a deep link that doesn't land, sideways scroll at phone width, a nav drawer that won't open.
  • What it can't see: overlap, clipping or ugly wrapping. Look at the screenshots in results/site-check/.
  • Commit what the scripts changed in docs/, with the element it documents.
  • The bundle is git-ignored: its hashed chunk names churned every diff.
  • Never edit site/_assets/ or docs/__data/, but the hand-kept pages.json5.
  • The theme menu in the masthead and the top bar is <ui-theme-menu>: the viewer's pick, light or dark, applied to every shadow root at once.
  • The theme bench page is the theme editor at full width: Spell's real pages side by side in the theme being made, its big choices and every token, live.
  • How themes work, and how to make one: README-themes.
  • Not deployed anywhere yet: it runs from the page server. A static host would take docs/ with _assets/ copied in beside it, through its icon-packs link (cp -RL); every bundle URL is relative.
  • The comments' addresses, /_epic/..., answer only on Spell's own servers.
  • A watch rebuild leaves old hashed chunks behind; yarn site:build clears them.
  • README-site: every script, file and environment variable, and the library's own tools
  • README-components: every family, with a picture
  • Custom Elements: how the elements the pages show work
