Spaces and the Cloud

 
@spell/examples/Solitaire/Solitaire.spell
└──── group ──┘ └project─┘ └──── file ──┘

One file of the Solitaire example, named by what it is rather than where it is. The editor, the command line, an importing project and the server all write that same address, and one function turns it into a folder. A SPACE is a person's or an org's folder of projects; this page is how they're named, how things in them are saved, and what Spell's server does to keep them shared and safe.

Written for: anyone working on where projects, people or a program's data live Checked: 2026-11-21, every command and file against that day's code The reference beside it: README-spaces; for a program's author, Data
  • Everything Spell names has ONE kind of address: a group, a project, a file, a folder.
  • Every thing has a built-in id, and saves by it: written whole inside what holds it the first time, a reference after. So a card in two piles saves once.
  • Saved files have versions, upgraded as they're read, and are checked against their class. The Spell declaration is the only description anyone writes.
  • People and orgs are Spell: the people library, compiled to a TypeScript library the server imports. A person is a readable __me.json5.
  • Your own projects live in spell.spaces, beside the kit's folder, in no repo.
  • Spell's server writes a space's data for its members, by role; projects part of it into another space; and takes it down, backs it up and exports it. 
address  = group "/" project [ "/" path ]
group    = "@" org "/" domain            built-in:  @spell/examples, @spell/library, @spell/test
         | person "@" org                a person's own:  owen@spell
project  = name                          one part, no dot;  lower-kebab by convention
path     = file | folder "/"             a file has a dot;  a folder ends in a slash
  • Only the group is looked up; everything after it is a folder or a file in the group's folder.
  • One function turns an address into a folder, SpellUrls.folderFor(), so nothing can disagree about where a project is.
  • If you know npm, @spell/library/people reads like a scoped package. The difference: no registry and no install. A library on your disk is importable the moment it exists.
  • The old forms (@system:examples:Solitaire) are read nowhere.

  • Every URL holds the address as it is, and one class makes them all, SpellUrls.
  • Spell never sees a path on disk. Under node, spaces' disk reader answers the same URLs.
  • No old URL is redirected: an old address answers "not found".
  • A space stands for every group in it (spell compile @spell), a group for its projects; spell asks which one, or --all takes them all.
  • @here is the project in the folder you're in: @here/Card.spell is ./Card.spell.

Two friends, saved by the core's Saver: both cores write and read this same file, savedById.expected.json5, so they agree.

  • Every thing and list has an id, built in; a program that declares one is refused.
  • Read before it's set, it's made up, like person-k3x9q2mf, from real randomness, never the seeded random.
  • Set it like any property: a new person with id = "owen".
  • A thing is written whole the first time it's reached, a reference after: { "$ref": "Card#ace" }. So a saved game is a handful of entries, never a file per card.
  • A reference to a thing in ANOTHER place names it: Person#matt@three-degrees.
  • Every key the JSON uses for itself starts with $: $type, $items, $ref, $in, $version.
  • a person is saved in its own file gives a kind an entry of its own.
  • a person version 2 renames name to names compiles to Person.v2RenamesName = "names"; ... drops nickname likewise.
  • to upgrade (a person) to version 4: does the rest, on a thing read from an older file.
  • The loader brings an older entry up step by step; the next save writes the newest version.
  • Adding a property needs no new version: only renaming, dropping or changing one does.
  • checkEntry(), in checking.ts, checks each property is one the class declares, of its kind, and says where: dates[0].label: label is text, not a number.
  • jsonSchemaFor() writes the same as JSON Schema, for VS Code only: a compile writes it into the build folder, never committed.
  • The kit's VS Code settings map __me.json5 to Person's schema and __org.json5 to Org's. 
an org is a thing
	it is saved in its own file
	it has a name as text
	its "members" is a list of memberships
  • No schema file, no ORM: those sentences are the schema, in People.spell.
  • The library compiles to TypeScript (its ts/lib target, people.lib.ts), which the app, the people store and spell import.
  • A person, Person#owen@spell, is __me.json5 in their space; an org, Org#spell, is __org.json5 in its folder.
  • The people store, PeopleStore, reads and writes them a file at a time, keeping every comment. A file with a problem is read anyway, the problem listed.
  • The editor's "You" panel edits this machine's person through /api/people/me; their orgs and roles are read only.
  • Spaces' own names (__me.json5 ...) are known by a list, never by the __ alone, so Python's __init__.py still lists as a file.
  • The code is the app folder's spaces, app/src/spaces: its models (browser-safe), projects on disk, and the servers that serve them.
  • Its route module is the app's part of the kit's page server. The editor reads files at /spaces/... and saves through /api/projects/....
  • A compile writes to the build folder, app/build/, which mirrors the project's address and is never committed.
  • Python's programs are served by spell_quart, a uv project in the same folder.
  • Each person's preferences are a JSON5 file in their space, __prefs/, kept by SpacePrefs.
  • Spell's own files are JSON5 (__project.json5, declarations); the kit's VS Code settings open them as JSON with comments. 
family cookbook is a data folder at "@family/cookbook"

A Firebase app keeps its rows in a database a console sets up. Here they're files in a space's folder, @family/__data/cookbook, one per thing, written through Spell's server and read straight from the files.

  • A space's folder is written by its members: a viewer reads; an editor adds and changes rows, and removes only their own; a manager also publishes, removes anything and adds people.
  • Every row is the space's, with by naming who saved it, so two people editing one recipe keep one record.
  • Reads skip the server: /api/reads/spaces/<address>/, with a credential for the whole space, good for 30 days. Every read checks the member list again, so someone who leaves is cut off at once.
  • An org's roles are kept once, in its Admin space; every space's list is worked out from them. spell space org audit says where a list differs.
  • Sign-in is an emailed link and a 6-digit code, invite only.
  • A projection writes part of one space's data into another, where its readers can see it: the published sheet is a projection of the sign up sheet.
  • Its lines say where it goes, which fields it shows, and which rows.
  • spell space projection list <space> lists them; rebuild writes one again from nothing (SpaceProjections).
  • One retry queue, on the server's disk, carries every write that has to go somewhere else: a projection's target, an inbox's copy, a mail.
  • spell space takedown hide | delete | restore | list: a Spell admin hides a record, a space or an account, with a reason, logged in the folder's own log (Takedowns).
  • A refusal says "taken down" and where to ask, never why: HTTP 451, with the abuse contact, abuse@spell.spaces unless SPELL_ABUSE_CONTACT says otherwise.
  • Each space has public read and public write, off until a manager turns them on, in __settings/space.json5.
  • Limits: 1 MB a thing, 100 MB a space. A save over either is refused, and stays on the page.
  • spell space backup now | list | status | restore: every space copied nightly, a week kept, a missed night logged (SpaceBackups).
  • spell space export <space> <folder>: a space as plain JSON, which a program runs on with one line changed. spell space delete deletes one for good. 
a "status" is a thing:
	- it is published as "xyz.statusphere.status"
	- its "status" is required text, with maximum length 1
	- its "created at" is a required date
  • spell space lexicon read turns another app's Lexicon, AT Protocol's schema language, into a Spell type, as above: Bluesky's Statusphere example.
  • spell compile writes a Lexicon beside each library type's JSON Schema.
  • spell space lexicon publish writes a library's published types as schema records, and prints the DNS record to make.
  • The cloud is its own server, apart from the page server, on port 4949: spell space cloud serve, for a tunnel or a proxy to give it an address (SpellCloud).
  • It serves sign-in, project data folders, the terms page and the built-in programs, and nothing else.
  • spell space cloud status exits 1 when it isn't running, or a backup night was missed.
  • No public address yet, and no real mail: codes are read with spell space cloud mail.
  • Pending sign-ins live in memory: a restart loses them.
  • A hidden account stays signed in where it already was; shared rooms don't check takedowns yet.
  • Backups cover spell.spaces only, not the sign-ins.
  • Orgs live on Spell's server, shaped like AT Protocol's Spaces; Spaces itself was tried on its alpha, not used.
  • Only the JavaScript core checks a saved file, and Python's core doesn't upgrade old files yet.
