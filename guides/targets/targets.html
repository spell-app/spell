@core.as_action({"undone_as": "Play Fizzbuzz"})
def play_fizzbuzz() -> None:
    """each number from 1 to 100, as one of four events:  fizzbuzz, fizz, buzz, or a plain number"""
    for number in range(1, 101):
        if (number / 15).is_integer():
            core.trigger("fizzbuzz", number=number)
        elif (number / 3).is_integer():
            core.trigger("fizz", number=number)
        elif (number / 5).is_integer():
            core.trigger("buzz", number=number)
        else:
            core.trigger("plain-number", number=number)

That's Python as a Python programmer writes it: range(1, 101), elif, PEP 8's names. It isn't JavaScript translated. The parser reads the program ONCE, into a tree of what it means, and each target has its own writer that turns the tree into that language's code. Then every test program is run on every target, and each must print the same thing, line for line.

Written for: anyone about to change what the compiler writes, add a target, or read a Spell tree Checked: 2026-11-21, every command and output on this page run against that day's code The reference beside it: README-targets, and for the core each target runs on, README-core
  • ONE tree in the middle: languages on the way in (English, Spanish), targets on the way out. N plus M, never N times M.
  • Four targets:
    • js/solid: JavaScript on Solid, compiled for every project, since everything runs it
    • ts/solid: the same program as a Solid developer types it, with types, decorators and JSX
    • ts/lib: a project's classes as one TypeScript file, for code that isn't Spell to import; its files that draw, e.g. the app that shows them, and its stylesheets are left out
    • py: Python on spell_core, the core's Python twin; a program that draws becomes a web app
  • A writer is a class with one method per kind of node. A new target is a new class, not a new compiler.
  • Compiled code counts positions from 0, as JavaScript and Python do. How a project's SPELL counts is its own setting.
  • Proven two ways: snapshots pin each target's code character for character, and the core contract runs every test program on every target.

  • Code goes to the build folder, never committed. Only what others import or edit stays beside the source: the library and the Python web app.
  • Every project gets js/solid, whatever it asks for.
  • A project asks for the others in its project file, __project.json5: "targets": ["js/solid", "ts/solid"].
  • spell compile <project> --target py adds one for a single run; --stdout prints it instead of writing it.
  • spell run <project> --target ts or --target py runs one; js, or none, is the default.

JavaScript and TypeScript draw with Solid, through the core's drawing.ts. A value that changes updates only its own node: turning a card over changes that card, and nothing redraws the board.

  • JavaScript has no build step, so no JSX, decorators or types: it runs as it is.
  • Each drawn thing sits in its own error boundary: a broken card shows a stand-in, and the rest keeps drawing. In TypeScript that's @drawn on draw().
  • A view shows as its own element. JavaScript makes its <solitaire-card> as the page runs; TypeScript writes the class out, CardElement, and defines the tag with core.useElement(Card, CardElement), so the type checker sees it.
  • Spell and Spell UI share one reactive engine, in spell/util/reactive.
  • A writer has a method named for each node class it writes: ASTIfStatement().
  • A node with no method of its own is written by its nearest base class's.
  • TSWriter extends JSWriter, and LibraryWriter extends TSWriter: each overrides only what it writes differently.
  • A writer writes a child with this.write(child), so a subclass's overrides reach every child.
  • A node no method writes makes the writer throw, naming the node.
  • Methods are found by class NAME, so every build keeps class names.

Under every writer is ProgramWriter. It reads the whole project before writing a line, so it knows a card's rank is one of thirteen values, not just some text. It holds what changes from one language to the next:

  • how names are cased: camelCase for JavaScript; snake_case and UPPER_CASE for Python
  • where positions start (section 7)
  • each language's file separator and import lines
  • Every target keeps the line of Spell that made a stored property, as a comment above it.
  • A list's own methods where it has them, events from core, and plain loops.
  • Of the 207 examples in Spell's syntax table that carry their output, TypeScript writes 184 character for character as JavaScript does. The other 23 add a type, declare a member added from outside its class, or draw in JSX.
  • Types where Spell knows them: Suit and Rank from their values, parameters, List<Card>, lists as const.
  • Where a program never says a type, what it does says it: a property's from the values it's given, a method's from what it returns.
  • A type Spell doesn't know is written any /* spell: type unknown */, never a bare any, so every gap shows and can be counted.
  • tsc checks each test project's TypeScript, and its report is pinned beside it.
  • The catch: it never runs as it is. spell run --target ts builds it (esbuild, then Solid's compiler) and runs it under node. A program that draws can't open in a browser that way yet.
  • The tree says what a program MEANS, not how one language writes it. Its 14 operators are meanings: and, or, equals, not equals, exactly equals, not exactly equals, less than, greater than, at most, at least, plus, minus, times, divided by (AST_OPERATORS).
  • Each writer spells them its way: and is && in JavaScript and and in Python.
  • plus adds numbers or joins text: a writer tells which from the two sides' datatypes.
  • Spell's own values stay values: up, which each writer quotes its own way.

Compiled code counts from 0 on every target, as its own language does: the first tile of a rack is rack[0]. How a project's Spell counts is a setting only the compiler reads.

  • Spell counts from 1, unless the project file says "listsStartAt": 0. Then the hover text and the Type Explorer say "counts from 0".
  • Only NUMBERS change: item 3 of the deck, the position of the queen, a loop's position.
  • Ordinals don't: the first card is the first card either way. Nor do negative positions: -1 is the last.
  • Neither core takes a start: deck.position_of(ace), with nothing more.
  • A number written out is worked out as it compiles: item 4 of the deck is core.getItemAt(deck, 3).
  • One known only when it runs goes through position(): core.getItemAt(deck, position(n)), and in Python position(column).
  • A position coming out goes back through spellPosition(); a range's end through endPosition().
  • item 0, counting from 1, is nothing, like a position past the end.
  • The helpers are in both cores: positions.ts and positions.py.
  • Counting from 0, nothing needs turning: the test project lists-from-zero compiles with no helper at all.
  • Counting from 0, tiles 0 to 2 of the rack is rack.slice(0, 3) in JavaScript, rack[0:3] in Python.
  • Spell's ranges include their end, and a slice leaves it out: the compiler adds the one.
  • What compiled Python imports, for what Python has no word for: from spell_core import core, Thing, List, prop, h, and only what it uses.
  • A uv project for Python 3.12 or later, in parser/src/py/core. Its dependencies are empty: the standard library only.
  • Each module is the twin of one in the JavaScript core: things, lists and their guards, types and equality, Spell's tests, events and pauses on asyncio, JSON, drawing as HTML text, the seeded random, the position helpers.
  • Its console prints exactly what node prints: 3.0 as 3, yes and no as true and false.
  • It runs a compiled program by itself: python -m spell_core.run <program> --seed n.
  • One seed deals the same cards in both languages: both cores have the same number generator (Park and Miller's) and the same shuffle.
  • The core's method list, core.declarations.json5, is written from the core's docstrings by yarn core:gen:declarations in the parser folder; a test fails when it's out of date.
  • A Python test checks spell_core against it, in snake_case. A missing name fails, unless it's listed, with why, in not_ported_yet.json5.
  • That list fails too when it goes stale: a name it lists that spell_core now has.
  • Today it lists 107 names, in 21 groups: most are a browser's only, or a page's actions, drags and sounds.
  • The core reference shows the list as a page, each name with Python's name for it and whether spell_core has it yet.

A Python program that draws runs as a web app: Python keeps the logic, and the page draws what Python says. spell run <project> --target py serves it and opens it in your browser, until Ctrl-C.

  1. The page opens, and gets the whole state: every thing as JSON, each with an id.
  2. A click on the page calls Python: this.turnOver() is sendCall("turn_over", [], this).
  3. Python runs it, and sends back a patch: only the things that changed, each whole.
  4. The page reads the patch INTO the things it has, by id, so what draws them redraws.
  • Both cores have a state writer and a mirror: state.py and state.ts.
  • A thing's first mention is whole; each later one is {"@id": "3"} alone, as JSON-LD writes a reference. So a card in two places stays one card.
  • A saved state, stateById.expected.json5, is written and read back by both cores' tests: they agree on every character.
  • A game per visitor.
  • Python's target writes two more files: the page half, <Project>.elements.spell.js, and a short Quart web app, <Project>.app.py, with every route spelled out, for you to grow (quartApp.ts).
  • The app runs on spell_quart, in the app folder (spell_quart).
  • Each compile rewrites the app only while nobody has edited it: its first line holds a hash of the rest.
  • Snapshots: every frozen test project's code, for each target, is pinned beside it, with what tsc and pyright say about it. spell content check --bless rewrites them; then read the diff.
  • Rule tests: each rule's tests say what both JavaScript and TypeScript write (README-parser, "Testing rules").
  • The core contract, contract.test.ts: every test project, compiled for each target, runs headless from seed 1, and must print the same thing, its drawing included.
    • Only stdout is compared: a dumped thing goes to stderr, in each language's own look.
    • Python runs the projects its writer writes so far (PYTHON_FIXTURES).
  • pyright checks every test project's Python, as Python 3.12; ruff and pytest check spell_core, in the parser folder's yarn lint and yarn test.
  1. A writer class, extending the nearest one that writes like it.
  2. An entry in SP.TARGETS: its name, writer, file ending, and what its runtime can do.
  3. A line in the core contract test.
  4. A core, if the language is new: Python's is the worked example.
  • A drawing program compiled as ts/solid can't open in a browser from spell run yet.
  • Python's type hints are thinner than TypeScript's: where TypeScript says rank: Rank, Python says rank: Any.
  • 107 of the JavaScript core's names aren't in spell_core yet.
  • Python's writer can't write a function's named arguments yet: the test project todos-form-based has no Python snapshot.
  • A kind of node the Python writer can't write stops the compile, naming it.
  • 🌱 WebAssembly is planned, not built: --target wasm answers in one line, above.
