Background Agents

> /bg "docstrings" 2 add a docstring to every export in util/string.ts
started:  skillz-docstrings (2 agents)

That one line, and the panel is yours again: a helper named skillz-docstrings does the task, and its report comes back as a notice when it's done.

It's & in a shell, with three differences. Each job has a name and a budget; it shows on the epic page while it runs; and you can steer it mid-task with a note.

The rules: the /bg skill, the full text of the standing rule a repo's CLAUDE.md names "Delegated work"; the list's verbs, epic agents --help In an epic: README-skills, "The session answers; agents build" Written for: you, the Claude sessions starting agents, and whoever changes /bg or epic agents Checked: 2026-11-21, every command and file against that day's code the three forms · 3 lines 
/bg ["name"] [n] <task>     start one:  /bg "docstrings" 2 add a docstring to every export in util/string.ts
/bg ?                       what's running:  name, status, age, task
/bg stop <name>             stop one
  • "name", a quoted first word. None: Claude makes one up from the task, 1-3 words, kebab-case (string-docstrings).
  • n, a whole number 1-5 next: the most agents the task may use IN ALL, the helper included.
    • Default 1: the helper alone. /bg 3 is the helper plus up to 2 of its own.
    • A hard cap, unlike the standing rule's "up to 5, unasked".
  • The rest is the task, word for word. No task: Claude asks for one, and starts nothing.

Every agent a session starts, by /bg or on its own, is NAMED and LISTED while it runs. So you, and Claude, can always tell what's in flight.

  • The real name is a prefix and the name: the epic's name, else the worktree's, else main. In epic skillz, /bg "aaa" is skillz-aaa.
  • An agent's own helpers add to its name: skillz-aaa-tests.
  • Claude Code's Agent call has no name field, so the name goes first in its description (skillz-aaa: docstrings in string.ts), which is what Claude Code shows.
  • A name already running is refused, and Claude takes aaa-2.

The session does only this, quickly, and never reads the files the task names: the point is a free panel.

  • A fork is a copy of the session that sees the whole conversation, so "fix the thing we just talked about" works as is.
  • The catch: the VS Code panel's sessions had no fork agent type (2026-10-07). The call fails with Agent type 'fork' not found, and the skill makes the same call with general-purpose.
  • That helper sees NOTHING of the conversation, so the session fills in the brief's Context line: which thing, which files.
  • A helper's own helpers are ordinary agents (general-purpose, Explore ...), never forks.

The helper's prompt is a template in the skill, filled in once. It carries the task word for word, a Context line, the checkout (and worktree, branch), the epic and its page, the budget, and these rules:

  • The house rules: the repo's and the folder's AGENTS.md and the house style they name. Stage, and never commit unless told; in an epic, its own merge (below) is the exception.
  • The epic folder at its real path: epic pages, guides and logs are edited where they live, never git-added. A turn-end hook commits them.
  • No questions to you: a choice you might make differently is taken, then recorded as a calm judgement call on the epic page, its title at most 30 plain words, read cold.
    • It stops only on a risky one: deleting or overwriting work, publishing, changing what the task means.
  • Status cards in short paragraphs: an item's card opens with one sentence saying what happened, then short paragraphs or bullets; epic update refuses a paragraph or bullet over 50 words, so the long story goes in the item (epic details <epic>#<id> --append).
  • Claims: before changing a file, it claims it (epic agents claim), a file, a folder or a glob. A file another agent claimed is refused, naming the holder, and it leaves that file alone.
  • Merging main in with epic worktree merge-main --as <name>, which never moves aside a file another running agent claims.
  • Tests in three tiers:
    1. per change, only the tests beside what changed
    2. before merging, each touched folder's unit tests, in its turn: epic turns run test -- yarn test:unit
    3. after merging, the full suite, only if epic agents last says it's the last agent standing; what that finds becomes an issue
  • In an epic, merge at once: once its work is done and checked, it merges into main itself, whenever that merges cleanly.
    • The steps: commit by path, merge main in, unit tests, epic merge <epic>, mark the item fixed.
    • It can't: it says why in its report and on the item.
  • Never mark itself done: epic agents done is the session's, when the report arrives. Done early, the redirect waiter stopped while the agent still worked.
  • Its last message is its report: what changed, where to look, checks with numbers, judgement calls, and a question for you last.

While any agent of the epic runs, the epic page's header counts them, after the step label at its right: 2 🤖, the robot button. Click it for a popover, a row per agent with its task, age and the notes sent to it, and a box under each.

Type there to change an agent's course, without typing into a busy session.

  • The waiter's other exits: 3, nothing runs any more (don't restart it); 2, an hour passed (restart it while agents run).
  • An agent another session started keeps its notes untold, for that session's waiter.
  • A row updates in place as the page polls, so a note you're typing keeps its text and its focus.

The edge: a note reaches the agent only through a session that's waiting. A session that has ended can't pass it on, and the note stays untold.

Going heads-down on something else? Type /focus in any session, with a reason if you like (/focus the demo).

  • Every running epic session keeps building what's in flight, merges what's clean, and asks you nothing.
  • /back turns it off: each session posts its own status in its own window, what's waiting on you first.
  • The idle epics with news are listed in the session where you typed it.
  • It's one switch per machine (epic focus on | off | status, and summary for what happened meanwhile); a session started meanwhile hears it from a session-start hook.
  • The edge: Codex can't message another session, so there each session reads it at its next turn.
  • Its notice wakes the session, which runs epic agents done <name>. That prints how long the agent worked, from its transcript (skillz-aaa done: took 21m), and logs it on the epic page.
  • The reply opens with a bold line of its own, Agent skillz-aaa came back with:, then the report in short, with links. What you can't do or see yet gets a bold line of its own.
  • A question only you can answer goes in the question modal.
  • An agent blocked on this one is set active and started, in the same turn.
  • /bg ? shows the list as a short table. The list is the record, not the session's memory: it survives a compacted session, and shows agents other sessions in the epic started.
  • /bg stop <name> stops the agent's task, then marks it done. Its staged changes stay; it won't stop another session's agent.

In an epic, the session you type to answers you and hands anything longer than a minute to a named agent. So several agents often share the epic's ONE worktree, and three things keep them out of each other's way.

  • Claims: two running agents never claim the same file, and a merge never moves aside a file a running agent claims. Claims go with the agent when it's done.
  • Turns: merges and full test runs take turns on the machine, first come, first served; epic turns run test -- yarn test waits for its turn, and epic turns list shows each kind's holder, since when, and whether it's stalled.
    • Three full runs at once drove the load to about 50, and tests failed on their timeouts.
    • A command silent and idle for the stall window is stopped, and the turn freed.
  • The last agent standing: only it runs the full suite after merging: epic agents last <name> exits 0 when no other agent of the epic is listed.

A VS Code restart ends every background agent with its session. The plugin wakes the session at once, naming each agent the restart cut off; it resumes each from its saved transcript, starts one with no task id again from its task, and says so in one line.

  • Where it's kept, git-ignored, and gone when empty: in an epic, agents.json5 beside its epic page; with no epic, .spell-agents.json5 at the checkout's root.
  • Only the command and the page server's redirect route write it, never Claude by hand. Several agents write at once, so every write is locked, and atomic.
  • It says what's running now; the epic page says what agents DID.

Two /epic forms that act on the session's OWN epic. With no epic, they say so and stop.

the forms · 7 lines 
/epic phase                      a new phase with no antecedents:  the text on the lines after says what
/epic phase J1 J5, t3            from those items (spaces or commas, any case)
/epic phase add-phases           named "Add Phases"
/epic phase t3 Retry Logic       both:  from T3, named "Retry Logic"
/epic start P3                   phase 3, now
/epic start J3 J4 T6             those three items, worked as one block
  <text on the lines after>      your input, word for word
  • /epic phase: a background agent drafts the phase, its page showing a spinner while it plans.
    • It writes symptom, changes, goal (each antecedent linked), files, verify, estimate, then its build plan.
    • Last, before a last Doc Review, unless you name a place ("after P11").
    • It queues each antecedent into the phase.
  • Phase numbers stay whole: a new phase renumbers the to-do phases after it, and items, links and P5 · Name text follow. A started phase after the place refuses the move.
  • /epic start with items: each is closed when done, and the block goes in ONE commit, titled <epic> J3 + J4 + T6: ..., so the page files it under each item. A phase out of order: said in one line, then started anyway.
  • A page server loads its route modules only when it starts. So after a merge, a server that ran from before it served the old routes, and a new page control (like the agents button) never showed.
  • Now spell server start, which every opener calls, restarts a server older than its code. It checks the files the server loaded, when the server kept a record of them; else, any code file newer than the server's start.
  • So after a merge or a pull, the next page opened comes from a fresh server.
  • The main checkout's server runs on port 4747 only, and never falls back to another.
    • A restart first stops an old server of this checkout still holding 4747.
    • Anything else holding it is an error that names it.
    • A worktree's server takes a new port at each start.
  • A restart of main's server leaves the editor's Vite dev server running, and the new page server takes it over, so open editor tabs don't reload. A change to the installed packages still replaces it.
  • The budget is a rule, not a fence: nothing in Claude Code counts a helper's agents: the cap holds because the brief says so. A helper that ignored it could start more, and /bg ? would show them only if it listed them.
  • The name is ours, not Claude Code's: an agent started without epic agents add has no name anywhere but its description; /bg stop finds the task id in the list, never in Claude Code's task list.
  • A restart cuts agents off: they are resumed from their saved transcripts, not kept running, and only while the session is woken.
  • Claude Code only: Codex has no background agents: there the session does the work itself, a step at a time.
