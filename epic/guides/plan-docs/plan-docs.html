That orange chip is an issue an agent fixed while you were doing something else. On a real epic page it carries two buttons: Accept the fix closes it, and Revisit, with a note, sends it back.

An epic page is the plan, the questions only you can settle, the calls the agent made without you, and the record of what was built, on ONE page the agent keeps true as it works. An issue tracker and a pull-request thread split those four across two tools, and the open ones get buried.

Here you review item by item, when you have time, and the answers come back INTO the items.

The reference: README-pages, every control's table; README-skills, the session and its agents Written for: you, reviewing epic pages, with Claude listening or not Checked: 2026-11-21, every command and example against that day's code Examples: LIVE, drawn by the same <epic-*> elements an epic page uses; click a line to unfold it. Review buttons show only on a real epic page being reviewed, never in a guide.
  • Mark for an hour and send once: every key, click or scroll restarts Auto Send's wait, and a note box you're typing in holds it. To send only when you press it, set the gear's Auto Send to Off.
  • An epic's own session listens by itself whenever it's open. Send with nobody listening, and the page server types /epic review <name> into the epic's session for you; you press Enter.
  • Claude's answers go into the items, not the chat: the chat only links them, so a long review stays readable.

The catch: your marks wait in a file on THIS machine until they're applied. Mark on the laptop, press Send on the desktop, and the desktop has nothing to send.

They stick to the top as you scroll, so where the build stands and where you're needed are one glance up. Nothing in them is written by hand: each draws itself from the page's data.

  • At the left, one line of crumbs, EPICS / <NAME>. A click on the name copies /epic resume <name>.
  • In the middle, while the page is reviewed: Send, the paper plane (section 6), and nothing beside it, so a long epic name never gets cut off.
  • At the right, the step pill: the phase under way (P13), else the next one to do, DONE, FUTURE or STANDING. While the plan is still being agreed, it says the stage instead, OVERVIEW or PHASES.
    • Red when every phase is done but items still need you.
    • Grey when the epic is paused, untouched for 3 days.
    • ONE spinner says Claude is busy: while a phase builds, or the session is at other work, the pill's own icon turns, and its tooltip's last line says what Claude is on (Claude: Building P35); while it answers what you sent, a blue arc round the plane instead.
  • After it, while agents the epic started are running, their count and a robot, 2 🤖. A click opens a popover, a row per agent with its task and a box whose words reach that agent mid-task (section 7).
  • The gear: Focus mode (while the page is reviewed), Auto Send's wait, and the page's theme.
  • An icon per section jumps there. A red badge on it counts what needs you; an orange one, what's your turn to pick, review or see.
  • At its right, a chip per colour of item with the whole page's count; each section has its own over its list.
    • A click toggles that chip: its items hide or show, and the others stay as they are.
    • Option-click (Alt-click) shows only that group.
    • The blues toggle together, and so do the oranges and the greys.
    • Turn off the last chip showing, and the next one in the row turns on: a list is never empty by accident.
  • Then one button that unfolds every section, or folds them all again.
  • No new-item button here: each item section has its own at its end (New todo, New issue ...).
  • The meta lines: the review command (/epic review <name>, copied on a click), the branch and worktree, the dates, the saga it serves, and the epic's guide once Doc Review has written it.
  • An orange pill under the first line when marks are waiting and no session is reviewing.
  • See Also: the pages the epic made or leans on (its guide, its details and choice pages, the guides it links), gathered by the page server each time it serves the page.
  • While the plan is still being written, a folded "Plan hung?" notice says how to restart it.

An issue tracker lets every project invent its labels. Every epic page has the same eight sections, in this order, with the same ids: a link to #todos lands on the todos of any epic page, a year from now.

Section Its link What it holds
1. Overview #overview a two-sentence summary, the kickoff prompt (folded), the estimate added up from the phases, then the plan in numbered sub-sections (#o1 ...)
2. Phases #phases a block per phase, P1 · Short Name (section 4)
3. Questions (Q1 ...) #decisions what only you can decide; the answered ones are the decisions
4. Judgement calls (J1 ...) #judgements choices the agent made without you, "chose X over Y because Z"
5. Todo (T1 ...) #todos work still to do, and limits the plan accepts (marked limit, drawn grey)
6. Issues (I1 ...) #issues problems found, open until fixed
7. Manual tests (M1 ...) #tests what you check by hand before merging: a Step, and what it Should do
8. Log #log one entry per commit, newest first, with a chip per phase and item it names

Three more show only when they have something to say, and the eight never move for them:

  • 0. While you were out (#away), above the Overview: what Claude did since you last pressed Done reading, and what needs you now, a Read on each line. A finished phase ages out of it after 3 days.
  • Choices (#choices), between the Overview and the Phases: an open-ended list you pick from, round after round.
  • A report, after the Overview: what a run wrote for you, like an overnight /bedtime.
  • Every phase and item has a short id, so you can name it in chat: "start P3", "J7 is fine". An id never changes, and is never reused.
  • A decision (D7) is a question born answered: it lives in the Questions.

A section hides while it's empty, and shows the moment it holds something. While you review, an empty section with a New button stays, so you can add the first item.

No plan mode, and no plan in a chat: a new epic is agreed on its page, from its first minute, in three stages. Each ends with your Accept.

Start one with /epic <name> alone, and its Overview opens with a kickoff box.

Both open, styled, with their code coloured.
  • A judgement call or issue is CALM by default, yellow (a call grey), and red only when it would surprise you: it goes against something you said, narrows what you asked for, or needs your answer before work can go on. Click its chip while reviewing to flip it.
  • A todo marked limit is a limit to know about, not work: grey, with no buttons to do it.
  • A plain todo can be flagged red as a reminder (epic update seo#T3 --loud): red until you review it, its buttons still a todo's. --calm puts it back to yellow.

The chip's colour is the item's state, which the tool works out from its status and your marks on every edit. Only red and the two oranges ask for you, so you can read a page by its colours before you read a word.

Colour Means Live
red needs you: an open question; an unreviewed call or issue that isn't calm; a todo flagged as a reminder Q3, J7
orange your turn: a fix to review, or the agent's options waiting for your pick I4, Q5
light orange what you asked for is finished: an issue or todo filed from your own words, closed, until you see it T9
yellow open, not urgent: todos, a calm issue, a reviewed call T4, I3
blue with the agent: an Underway card, the spinner; dotted, queued and not started I1
green decided or done just now: an item for a day after its last change, then grey Q8
grey no longer relevant: canceled (struck through), a limit, a calm judgement call T6
  • Approving a green item greys it at once: green says "new since you looked".
  • Under the colour, an item's status is open, decided (an answered question), done (closed, never removed) or canceled (struck through; epic reopen undoes it).
  • Which state wins when several apply, row by row, and the colours of every other kind of page: README-pages, "Colours".

A pull-request review is a batch: you comment, then you submit. This is the same idea, except the batch can wait a day, and the answers come back as edits to the plan, not as replies stacked under your comment.

The edge: the wake happens once per epic per 10 minutes, and not at all in airplane mode or when several sessions are titled for the epic. Who it picks, in full: README-pages, "How Send wakes a session".

In an epic, the session you type to does almost no work itself. It answers within seconds, files what you ask for as items, and hands anything longer than a minute to a named background agent.

  1. Your Send wakes it, with a list of your marks.
  2. It applies the mechanical ones at once: approvals, picks, new todos, Do this, a todo's plane or x, new items, Accepts, Seen and Read.
  3. Each revisit asked now gets a blue Underway card, and a background agent writes the answer into the item; the card turns green. An answer that offers options turns the item ORANGE: your pick.
  4. The page updates in place: the buttons clear, and the chips show the result.
  5. The session waits again, costing nothing. Killed mid-wait, the page says nobody is reviewing within 90 seconds.
  • Ask for a fix in the chat mid-phase, and you see it on the page at once: an issue, your words as its body, blue, an Underway card naming the agent, any picture you pasted shown after the words.
  • Several agents share the epic's one worktree. Each claims the files it will change, commits only its own, takes its turn for merges and full test runs, and merges its own work into main the moment it's done, so you see it without waiting for the phase's end.
  • Tests run in three tiers: the tests beside each change; each touched folder's unit tests before merging; the full suite after merging, only by the last agent standing (epic agents last).
  • Each agent shows in the header's 2 🤖 popover while it runs. Type in its box to steer it: the session passes your words on mid-task (Background Agents).
  • A VS Code restart ends every background agent with its session. The session is woken at once, resumes each agent from its saved transcript, and says so.

The catch: Codex has no background agents, so there the session does the work itself, a step at a time, and hears your Send only while it waits (epic inbox wait). In a scripted claude -p run, the inbox poller stands down at once, so the run never waits on it.

Marks are for items. For anything else (a sentence of a guide, a row of a table, a line of the Overview), there's a comment: a thread anchored to the words it quotes, much like a code-review comment on a line.

  • Press the bullhorn beside a block (a section, table, code block, card, item or phase field, or the page's header), or select text and press ⌘-I (Ctrl-I). The pane saves as you type.
  • Saved, it's a thread, C1, C2 ...: your messages, the agent's, and "thinking…" while it works. Your turn, it goes orange, with three answers: ✓ that's good, reply, or × skip it.
  • The trash deletes a comment at once, with Undo for 6 seconds.
  • Comments ride the page's own Send. An epic page's go to that epic; a guide's, to the epic that owns it (wrote it, or its page links it); any other page's, to the standing feedback epic.

The edge: details and choice pages take no comments, since each sends its answers its own way; nor do templates.

Airplane mode lets you work on epic pages and guides with no internet and no Claude: everything saves on the laptop, and Claude takes it when you land.

  • Before the flight: /airplane. It checks the laptop is ready (page server, offline pages, the extension), asks which running sessions to park, and turns airplane mode on.
  • On the plane: open an epic page from the Review tab's list button ("Review: Open Epic..."), any other page from "Review: Epics Home".
  • Mark and comment as usual. Send isn't needed: every mark is taken at landing, sent or not.
  • A new epic: the Epics list's "New epic" writes a future epic at once. At landing, Claude asks which to start.
  • After: /airplane land. Claude gathers everything you left, applies the marks, answers the notes in the background, then starts /epic review on the epic with most waiting.
    • Text you typed and never submitted is asked about, never acted on.

Claude edits a page only through epic verbs, from any checkout, so ids, colours and counts stay right. The ones you'll see in a session's output:

epic ... Does
create <name>, stage makes the page (/epic runs it); sets its stage
add-phase, phase <name>#P3 done adds a phase; sets its status, writing Done
add <name>#J "..." adds an item (J, Q, I, T, M or D), printing its id; refuses a title over 30 words
update <name>#J3 underway | done | fixed | noted | promised a status card; --title gives a phase or item a new title
decide · choose · close · cancel · reopen answers a question, records a pick, closes, cancels or reopens an item
details <name>#<id> --more | --append adds More Details, or a reply
inbox wait | apply | done <name> reads and works through your marks
summary · items · open · test what's open; what a review walks; the page in the side bar; your testing

Every verb: epic --help, and README-cli. The rules for a page's data: PLAN-DOC.md; each element, live: The Epic Elements.

  • Marks are per machine. They wait in a file beside the page, git-ignored, until applied.
  • A page needs the page server. Opened straight from disk, it shows its prose unstyled: no buttons, no part files.
  • Find-in-page misses unopened bodies. Each item's and phase's body is a part file, loaded the first time you open it.
  • Send wakes only Claude Code. A Codex session hears it only while it waits on the inbox.
