## Bundle

### Method

- **Packaging:**
  - `solid-js`, `@solidjs/*` and `@spell/solid-element` are external, as a FUNCTION so subpaths match:
    `/^solid-js(\/|$)|^@solidjs\/|^@spell\/solid-element(\/|$)/` (`SOLID_EXTERNAL` in `vite.config.ts`).  `dist/`
    contains no Solid or fork code (a grep for `REACTIVITY_HALTED` / the fork's licence header finds nothing) and
    imports `solid-js`, `@solidjs/web` and `@spell/solid-element` by specifier.
  - **Two shared entries** (`SHARED_ENTRIES`):
    - `src/core.ts` -- the element core (`UIHost`, `UIElement`, `ElementDefinition`, `ContentPart` +
      `PartContext`, `Controlled`, `Cell`, `SlotContent`, `HostAttribute`, `IconGlyph`) AND the foundation it
      uses:  `$/util`, `$/vocabulary`, from `$/elements` `ClassBuilder` / `Shorthand` / `OwnerContext` /
      `NativeFallback`, `$/runtime` (the eager loader only), `$/icons` (`Icons`), `$/components/components.types`
    - `src/forms.ts` -- `FormElement`, `FormHost`, `Validator`, `MenuOptions`;  imported by `dropdown` only.
      `ui-button` is form-associated through the fork's `formAssociated` option alone (no value, validity or form
      API), so it stays on `core`.  `Controlled` stays in `core`:  it's the generic auto-controlled pattern
      (button `active` today, modal / popup / accordion `open` next), and in `forms` it would make every toggle
      button load `Validator` + `MenuOptions`.
  - Every component file imports through ONE path, `$spike/core` (and `$spike/forms` where needed), so family
    entries hold none of it.  The vocabulary, the sheet and the family's `<name>.fallback.ts` stay direct imports
    (they're the family's own).
  - Two chunking rules the split needed (both in `spike/shared/README.md`):
    - `core.ts` / `forms.ts` import `$/elements` LEAVES, never the barrel:  `export * from "$/elements"` would make
      `Validator` / `MenuOptions` core exports, i.e. core bytes
    - `forms` files import the element core through the `core` ENTRY (`./core`):  importing its leaves made
      Rolldown hoist everything `core` and `forms` share into a third chunk (`UIElement-<hash>.js`, 11.9 kB), and
      `core.js` became a facade
  - `rolldownOptions.preserveEntrySignatures: "allow-extension"`;  `button.css` + the button vocabulary land in a
    shared `button-<hash>.js` (the dropdown adopts `button.css`).
  - `package.json` `exports`:  `.`, `./index`, `./core`, `./forms`, one per family;  `sideEffects` lists the family
    entries, `index` and `src/identity.ts`, not `core` / `forms`.
  - The identity hook for the Solid 2 host page (`src/identity.ts`, `import * as` both Solid packages) is loaded by
    the `index` entry only:  in `core` it pinned ALL of Solid into every standalone build (button standalone
    80.7 kB vs 41.4 without).
- **Measuring** (`SpikeMeasure`, identical for every spike):  the spike's own Vite config, built in memory with
  entries `core` + `forms` + one per family;  every module is attributed to a bucket by id (`spike.config.ts`
  `groups`):  `library`, `core`, `shared:forms`, `own:<family>:classes|css|vocabulary|fallback`, lazy `runtime` /
  `icons`.  Each tier is minified (esbuild) and gzipped (level 9) ON ITS OWN;  a scenario sums, per family, only
  the shared entries that family's chunk actually imports.  `library (as used)` bundles exactly the bindings
  `dist/` imports from each peer specifier (tree-shaken);  the scenarios use it.  `library (full vendored)` is
  every export of the peer set, for comparison.
- **Standalone** (for comparison):  each family built ALONE with Solid and the fork bundled and tree-shaken, eager
  chunks summed -- the pre-shared-runtime way of measuring.

### Notes

- **Library size depends on tree-shaking.**  What the components actually use of `solid-js` + `@solidjs/web` +
  the fork is 26.7 kB (the "as used" tier);  every export is 59.6 kB.  The import-map pages still download the
  full set, because `src/identity.ts` (the Solid 2 host page's identity probe) imports all of `solid-js` and
  `@solidjs/web`, so the vendored copy can't shrink to the used bindings.  An app on Solid 2 ships its own
  tree-shaken copy anyway:  that's the "app already ships the library" row, the case this packaging is for --
  and on the Solid 2 host page the app and the components provably share that copy (Framework hosts).
- **The fork costs 1.5 kB more than what it replaces:**  3.67 kB min+gz vs 2.13 for `@solidjs/element` +
  `component-register` (the fork's `yarn measure`), for options, prototype accessors, converters, synchronous
  reflection, form hooks, lifecycle hooks and the error boundary.
- **`forms` keeps a button page lean:**  a page with only buttons loads `core` (14.6) but not `forms` (6.4);  the
  dropdown loads both.  `core` alone is smaller than the Lit spike's single `core` because `forms` moved out.
- **Fallback bytes are mostly decorator helpers:**  each `<name>.fallback.ts` is minified and gzipped on its own
  here (1.4-2.5 kB), and about 1.2 kB of that is esbuild's lowered-decorator helpers, repeated in every file with
  a decorator (`@proto static vocabulary`).  Net of them (and of `NativeFallback` in `core`, 0.8 kB) the
  fallbacks are 0.15-1.25 kB each (`docs/fallback.md`).  The same helper overhead is in every `classes` column.
- **Icon data is lazy**, and so is `UIRuntime` (27.0 kB).  `label` imports `parts.css` itself (a statistic's
  label adopts it), but the sheet is counted once, under `parts`:  a page with labels only also loads it.
- **Earlier numbers** (floor-based, Solid bundled into each build) are in the appendix.

## Ergonomics

### Declaring attributes and properties

- **Nothing is declared per attribute.**  `ElementDefinition` walks the vocabulary and hands the fork one prop per
  attribute:  `{ value, attribute, property?, reflect, converter: { fromAttribute, fromProperty, toAttribute } }`,
  keyed by camelCase canonical name.  The fork's props ARE `this.attrs`:  one signal each, already converted, typed
  from the `as const` vocabulary (`AttributeValues<V>`).  The old per-prop memo layer is gone.
- **Booleans:**  `Converters.boolean` (`yes` / `no` work) on BOTH paths -- the fork's new `converter.fromProperty`
  normalizes property writes (`el.primary = "yes"` stores `true`), which the old `convert()` layer did and Lit
  doesn't.  Reflection writes `""` or removes the attribute, never `"true"`.  Attribute writes never reflect back
  (`primary="yes"` stays).  Removals always apply (the old removal HACK is gone).
- **Values:**  localized values are canonicalized on the way in, from attributes AND property writes
  (`button.color = "verde"` on `<ie-boton>` stores `green`, reflects `verde` -- a smoke check);  arrays reflect
  comma-joined;  `json` kinds (`options`) observe their attribute but never reflect.
- **Reserved names:**  the fork THROWS at definition when a prop's property would shadow an element member
  (`hidden`, `title`, `style`, its own `dispose` ...) unless renamed with `property`.  The vocabulary's `property`
  is passed through (`dividerHidden`);  `safeKey()` and its dev warning are gone.
- **Pre-upgrade properties:**  the fork's standard upgrade step (captured in the constructor, re-applied through
  the setters) replaces the stash / restore (tested:  vanilla host, `options` set before `define()`).
- **Platform options instead of plumbing:**  `UIElement.define()` passes `BaseElement` (`UIHost` / `FormHost`),
  `shadowRootInit: { mode: "open", delegatesFocus }` (`@proto static delegatesFocus`, off for `ui-item`),
  `internals: true`, `formAssociated` (`@proto static formAssociated`), `keepAlive: true`, `errorBoundary`,
  `onError`, `fallback`.  No capturing registry, no final subclass.
- **Names:**  no attribute, event, slot or part literal in a template:  `this.part("button")`, `this.slot("icon")`,
  `this.emit("ui-toggle", ...)`, type-checked against the vocabulary.  Class WORDS of the markup contract are
  module constants.

### Templating

- JSX compiles to real DOM with fine-grained bindings;  the dropdown reads top-to-bottom like the contract.
  `<Show>` / `<For>` (keyed, so filtering never recreates a row that stays visible);  contract classes use Solid
  2's `class={[ITEM, { [ACTIVE]: chosen }]}`;  `<Dynamic>` for a part's varying root tag.  `aria-*` take strings.
- `Icons.svg()` returns a node, which JSX inserts as is (`IconGlyph`).

### Owner context and content parts

- **`PartContext`** holds the owner as a signal and a page-wide registry filled by `UIElement.define()`
  (`ownsParts` noun => tag => owner noun, the defined tags, the part tags);  resolution is `OwnerContext.find()`
  over the flat tree with a barrier at every registered non-part component.  An effect keeps
  `:state(in-<owner>)` in step;  the static `in-<owner>` class is never set.
- **Re-resolution:**  every connect after the first, through the fork's `onConnect` (NEW:  `keepAlive` keeps the
  controller across moves, so reparenting no longer re-creates it -- tested with a real detach, the SAME
  controller then resolves `in-card`);  `slotchange` in any spike element's shadow root, for elements entering and
  leaving;  once after first settle.
- **`ContentPart`** (in `core`) + a family base `PartElement` (in `parts`, adds `ContentPartFallback`) make the
  13 parts cheap:  six are 14-line files.  `--ui-part` is declared by `parts.css` on the ROOT, never the host.
- **`ui-header`** is part and owner;  `ui-label` in a statistic becomes its `.label` part;  `ui-icon` uses
  `direct` mode.  Owners that don't exist yet are `stub-*` elements (`StubOwner`).
- **App context reaches components:**  `UIElement.AppContext` is read by every controller;  on the Solid 2 host
  page, the app provides it around the dropdown and the component sees the app's value (owner adoption across the
  element boundary, through the fork's shadow-crossing owner lookup).
- **Platform limit:**  no event tells an element its assigned slot changed;  a foreign component re-slotting a
  part isn't seen until the part reconnects.

### Per component

- **Button, dropdown:**  the bulk of batch 0.  `<a>` vs `<button>` needs two JSX branches.  The dropdown releases
  its `UI.overlays` entry while disconnected (`keepAlive` keeps its state;  the overlay follows `connected`) and
  takes it back on re-attach (tested).
- **Icon:**  internals ARIA from one effect;  `variant` / `outline` pick the set.
- **Label:**  the most logic in batch 1:  five optional children, forwarded `aria-label`, context-dependent markup
  and sheets;  the `image` string attribute made it simpler this pass.
- **Parts, divider, segment, container:**  a render of 5-10 JSX lines each on the base class.

### What fought the library

- **Before the fork**, everything in the `ElementDefinition` / `UIHost` rows above:  no base class / shadow
  options / internals in `customElement()`, bare booleans parsing false, `true` reflecting `"true"`, pre-upgrade
  properties dropped, `removeAttribute()` ignored for bare booleans, a microtask reflection window, teardown on
  every reconnect, no error boundary, owner lookup stopping at shadow roots.  Each is now one fork module with a
  test that reproduces the original bug against `component-register` 0.8.8 (`spike/solid-element/UPSTREAM.md`).
- **After the fork**, only Solid 2 itself:  eager memos (`{ lazy: true }` on base-class memos, effects that call
  overridables created in `mount()`), no signal writes in owned scopes (the fork's hooks can run inside a Solid
  render, so `connected` and the fieldset `formDisabled` replay are deferred a microtask), writes landing on a
  microtask (`flush()` in tests), two-function `createEffect`.
- **`keepAlive` has a cost:**  a removed element keeps its reactive root until `dispose()` or garbage collection,
  so anything page-wide (overlay entries) must follow `connected`, not disposal.
- **Solid 2's dev diagnostics** flag the `classes()` memo as `WIDE_SCOPE_DEPS` (it reads every attribute);  the
  production build drops the diagnostic.

### What fought the conventions

- **Classes over functions:**  the library's unit is a render FUNCTION, `(props, { element }) => JSX`;  the spike
  wraps it in a controller CLASS (`UIElement`) created inside it, so `@proto static` defaults, methods over loose
  helpers and one class per file hold.  With `keepAlive` the controller now lives as long as the element.
- **Chunking vs `AGENTS.md`:**  `core.ts` / `forms.ts` import `$/elements` leaves (not the barrel), and `forms`
  files import `./core` instead of their peers -- both to steer Rolldown's chunk assignment (Bundle).
- `display: contents` hosts drop author box styles;  the examples size through `::part()` instead.

### Hot module replacement

Edit a component in `yarn dev` and every live instance updates in place:  same host objects, host attributes
and properties kept (the dropdown's `options` and controlled `value` included), no page reload.  Open
`demo/hmr.html` and edit `UIButton.tsx`, `button.css` or `button.vocabulary.en.ts`.

- **How:**
  - `@spell/solid-element/vite` (the fork's plugin, `solidElementHot()` in `vite.config.ts`, `apply: "serve"`)
    appends `import.meta.hot.accept(() => hotUpdate(import.meta.hot))` to each component barrel
    (`src/components/<name>/index.ts`, the modules that call `define()`).  An edit to a component class, its
    vocabulary or fallback climbs to its barrel, which Vite re-runs with the fresh modules.
  - `define()` is idempotent per tag, so the barrel's `UIButton.define()` would return the OLD class.
    `HotDefinitions` (dev only, the plugin's `setup` import) wraps it:  a DIFFERENT class of the SAME name
    defining a known tag is a new version, and takes over every tag the old one had -- `<ie-boton>` from the
    translation hook included -- through `UIElement.defineTag()`, which calls the fork's `customElement()`
    unconditionally.
  - The fork swaps each class's component, props (accessors, converters) and options in place, migrates each
    instance's values (property writes kept, attribute values re-converted, new props defaulted), then
    `hotUpdate()` disposes and re-renders every live instance (a per-class `WeakRef` registry, dev only).
  - CSS:  `?inline` component sheets self-accept;  `HotDefinitions.updateStyle()` re-registers the sheet by
    name (`button.css` => `button`) and `Styles.register()` replaces its rules in every adopted shadow root.
    Nothing re-renders.
  - A changed vocabulary also refreshes its English texts in `UI.i18n` (where no translation replaced them)
    and swaps the registration in `UI.vocabulary`.
- **Limits:**
  - Component-internal state resets:  a search query, the highlighted row, an open menu, an uncontrolled
    toggle's `active`.  Host state doesn't.
  - Anything the platform reads once can't change:  observed attributes (a new or removed vocabulary attribute),
    `formAssociated`, the host base class (`FormHost`), shadow root options (`delegatesFocus`).  The page reloads
    with `<ui-button>: observed attributes changed (+size), full reload`.
  - Shared code (`core`, `forms`, `UIElement`, the runtime, `HotDefinitions`) reaches several barrels:  the plugin
    reloads the page instead of letting Vite re-run every barrel against a fresh `UIElement` their live instances
    don't extend.  A module reaching ONE barrel (a vocabulary, a fallback, `SlottedItems`) stays hot.
  - A class renamed in the edit, or a vocabulary whose tag changed, defines as NEW;  old instances keep the old.
  - `UI.vocabulary.localized` (runtime-translated names) keeps the old vocabulary until a reload;  the elements
    don't read it.
  - `@solidjs/vite-plugin`'s refresh transform finds no components in class-based modules (checked:  no
    `import.meta.hot` in any transformed `src/**/*.tsx`), so it neither conflicts nor helps;  it stays on.
- **Test:**  `yarn test:hmr` (`test/hmr.e2e.ts`) starts the dev server, opens `demo/hmr.html` in headless chromium
  and edits the real files (restored after each scenario, then checked against their original text and
  `git diff --quiet`).  8 / 8 pass, ~4 s:
  1. `UIButton.tsx`:  every `<ui-button>` and `<ie-boton>` re-renders with the new markup;  same hosts,
     `primary` / `color` / `size` (set as a PROPERTY) kept;  segment and dropdown shadow nodes untouched
  2. `UIDropdown.tsx`:  re-rendered, `options` (property) and `value` (`fr`, shows "France") kept
  3. `button.css`:  the new rule applies in every shadow root;  same inner `<button>` node, same controller
  4. `button.vocabulary.en.ts`, the `or` text:  hot, `<ui-or>` shows the new text
  5. `render()` throws:  the native fallback and `:state(errored)`, the error logged, the segment still reacts;
     restoring the file recovers the same hosts
  6. a syntax error:  Vite's overlay, old code keeps running;  the fix re-renders
  7. a new vocabulary attribute:  the message above, then a full reload
  8. `UIElement.tsx`:  full reload
- **Cost:**  dev only.  The plugin appends ~180-250 bytes to each barrel and style module, plus `HotDefinitions`
  (5.8 kB of commented source) and the fork's registry (one `WeakRef` per element);  the fork's HMR paths sit behind `import.meta.hot`, which a build replaces with `undefined`.  `dist/`:
  byte-identical except `core.js`, where `define()` split into `define()` + `defineTag()` (+76 B min, +6 B gzip:
  the one production change, so HMR can re-define without duplicating `define()`'s body).  Library tier:  same
  min size, +4 B gzip (module order in the fork's `dist/`).

## Forms & accessibility

### Forms

- **Form association** is now the fork's `formAssociated` option;  form callbacks arrive as hooks registered
  during setup:  `onFormReset` => `FormElement.formReset()`, `onFormDisabled` => `UIElement.formDisabled` (the
  fork replays the last state to a late registration, so the replay happens in the component body and is
  deferred a microtask).  `FormHost` is now only the form-control API (`form`, `validity`, `checkValidity()` ...).
- `FormElement`:  `formValue()` feeds `internals.setFormValue()` (a `string[]` becomes a `FormData` with one entry
  per value);  `required` runs `Validator` into `setValidity(flags, message, anchor)` with `:state(invalid)`;
  reset restores the connect-time value;  a disabled `<fieldset>` disables the control.  All tested.
- **Submit buttons:**  `<ui-button type="submit">` calls `internals.form.requestSubmit()`;  `name=value` is sent by
  setting the button's form value for the duration of `requestSubmit()` (tested), because a custom element can't
  be the form's `submitter`.  `type=reset` calls `form.reset()`.
- **Known gap:**  pressing Enter in a text field doesn't find a custom element as the form's default button.

### Keyboard and focus

- `delegatesFocus` is the fork's `shadowRootInit`;  `host.focus()` focuses the inner control;  presses on the menu
  keep focus in the combobox;  blur outside the host closes the menu.
- APG combobox keyboard, all tested with real key events:  ArrowDown / Up, Home / End, PageUp / PageDown (10
  rows), Enter, Space (button trigger), Tab, Escape (routed by `UI.overlays`, top overlay only), type-ahead,
  Backspace removing the last label.  Tests set `UI.overlays.useCloseWatcher = false` so `{Escape}` is
  deterministic.

### Accessibility

- `aria-activedescendant` requires the listbox in the combobox's own shadow root;  rich `<ui-item>` content is
  PROJECTED into its row via a generated `slot` attribute on the author's element.
- The combobox is named from `placeholder` (else `text`, else `name`), the value text linked by
  `aria-describedby`;  a host `aria-label` is forwarded to the inner control (button, icon-only label).
- To satisfy axe's listbox rules:  the "no results" message is a disabled `role=option`;  dividers are
  `role="presentation"`.
- axe passes on every element-markup example (39 files) with `color-contrast` off (the original fragments fail
  it too);  `heading-order` is also off for `parts/header.html` and `segment/variations.html` (originals too).

## Error handling & native fallback

- **Boundary:**  the fork's error boundary (on by default, `createErrorBoundary` around each element's render)
  replaced the spike's `UIElement.isolate()` + `FAILED` set.  A throw in the constructor, in render, in a memo
  during an update or in an effect stays local:  the element stops rendering, a sibling keeps updating, new
  elements still render (tested for all three sites).  Without it (`errorBoundary: false`) the same throw logs
  `[REACTIVITY_HALTED]` and the sibling freezes (tested, last in its file).  Cost:  300 labels rendered in
  23.0 ms with boundaries vs 19.2 ms without (median of 5 in `isolation.test.tsx`, noisy).
- **Hook:**  `UIElement.define()` passes the fork's `onError` and `fallback`:
  - `onError` (runs outside any owner):  ONE `console.error` naming the tag with the cause
    (`<ui-button> failed:`), a cancelable, bubbling, composed `ui-error` (`detail: { error }`), `ready` resolved,
    the broken controller dropped.  The fork sets `:state(errored)`.
  - `fallback`:  unless `ui-error` was cancelled, the family's `@proto static Fallback` --
    `ButtonFallback.render(host, host.renderRoot, error, host.internals)` ... -- builds its native DOM into the
    shadow root, a microtask later (the boundary's own insert would clear the root after a synchronous build, and
    the dropdown's fallback must be attached to set its validity anchor).  Its handle is disposed with the element.
    An element without a fallback (groups, `ui-item`, `ui-or`) gets a bare `<slot>`, so its children stay visible.
  - Per-family fallbacks live in the family's chunk:  `UIButton.Fallback = ButtonFallback`, ...;  the 13 parts
    share `ContentPartFallback` through `PartElement`.  The markup is library-neutral (`src/components/<name>/
    <name>.fallback.ts`), so both spikes render the identical thing and the component's adopted sheet styles it.
- **Bytes per family** (`docs/fallback.md`, net of shared code and decorator helpers, gzip):  base
  `NativeFallback` 0.80 (in `core`), button 0.68, dropdown 1.25, icon 0.32, label 0.30, parts (all 13) 0.40,
  divider 0.23, segment 0.20, container 0.15 -- about 3.5 kB for all eight.  In this build, each family's
  `fallback` column (above) is 1.4-2.5 kB because every file carries its own lowered-decorator helpers.
- **What degrades** (`docs/fallback.md`):
  - button:  `ui-toggle`, the icon glyph and icon / label slots, the joined label, `animated`, the spinner;  a
    host click handler can't veto submit
  - dropdown:  a native `<select>` (multiple, optgroups) instead of the combobox:  no search, additions,
    clearable, max-selections, value labels, option icons / images / descriptions, `ui-open` / `-close` /
    `-search` / `-add` / `-remove`;  the native select's keyboard pattern;  `readonly` becomes disabled.  Form
    value, validity, `host.value` and `ui-change` keep working.
  - icon:  the glyph;  label:  delete button, icon, image;  divider:  icon shorthand;  parts:
    `:state(in-<owner>)` styling;  everywhere:  idref ARIA can't cross the shadow boundary.
- **Tests:**  `spike/shared/tests/fallback.cases.ts`, library-agnostic, run by `src/errors/fallback.test.tsx`
  through a `FallbackAdapter` (`breakRender()` makes a RENDERED element's next update throw:  its controller's
  `extraClasses()` throws and one `keyOnly` attribute is flipped and back).  All 7 pass:
  - a throw in render shows the native fallback, with exactly one tagged `console.error`, one `ui-error`
    (bubbles, composed, cancelable, `detail.error`), `:state(errored)`
  - a cancelled `ui-error` keeps the fallback out
  - every family renders its fallback root (and is really `:state(errored)`)
  - a sibling of a failed element still updates;  a new element still renders
  - the fallback button submits its form with `name=value` (`a=1&action=save`), only during the submit
  - the fallback select starts on the chosen value, keeps the form value, and a change updates the form value,
    `host.value` and fires one `ui-change`
  - axe passes on every family's fallback (`color-contrast` off)
- **Demo:**  `demo/fallback.html` (via `yarn serve`, and a smoke check page) shows each family working beside its
  failed copy;  the failed submit button submits `[["action","save"]]`.

## Translation

- `UIButton.define("ie-boton", es)` and `UIDropdown.define("ie-desplegable", es)`, with a 20-line dictionary
  (`src/translate/es.ts`):  3 tests, `demo/translate.html` (dev) and `demo/smoke/translate.html` (from `dist/`).

- **Values:**  converters canonicalize on the way in, from attributes and property writes (`rojo` => `red`,

- **Events:**  localized (`ie-cambio`, `ie-alternar`).
- **Items:**  `SlottedItems` recognises items by definition (`UIElement.definitions`), so a translated item tag

- **Not strict:**  a canonical attribute name the dictionary doesn't translate still works on a localized tag
  (`<ie-boton basic>`).

  sneaks in silently.
- **`keepAlive` retention:**  a removed element keeps its reactive root until garbage collection or `dispose()`;
  page-wide registrations must follow `connected` (the dropdown's overlay does).
- **Full Solid vendored on import-map pages:**  59.6 kB for Solid + web + fork against 26.7 kB as used, because
  the identity probe imports everything;  moving the probe to a page-only module would let the vendored copy
  shrink like Lit's.
- **React rejected-change drift** (Framework hosts);  **no hydration** (SSR).
- **Runtime budget:**  the lazy runtime chunk alone is about 27 kB min+gz against a 20 kB plan budget.

## Foundation bugs

   order, so `[class*="top attached"]` never matches the static fragment;  the element emits
